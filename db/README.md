# DB-MIGRATION-01 — первичная схема MySQL/MariaDB

Схема предназначена для будущего единого источника истины TARKENSO. В ней предусмотрены игроки, bcrypt-хеши (без пересчёта), серверный баланс, Mute, медицинские параметры, прогресс гонок и уборщика, админправа, баны, составы организаций и глобальные данные кварталов/топ-10.

**Важно:** эта ветка НЕ меняет Pawn runtime. Пока не завершены тесты БД и обратная совместимость, сервер читает и пишет старые `scriptfiles`. Никакого параллельного двойного начисления денег не допускается.

## Запуск

1. Полностью остановить игровой сервер и сделать побайтовый архив папки `scriptfiles` (включая `.bak`, `.tmp`, .adm и .ban). Применять перенос на неподвижной копии.
2. Создать **пустую** БД MySQL 8 / MariaDB 10.6+ в UTF8MB4 и отдельного пользователя с минимальными правами. Применить `db/migrations/001_initial.sql` к пустой БД **один раз**, затем `db/migrations/002_start_region.sql` (в том числе при обновлении работающей схемы v1, заранее сделав резервную копию).
3. Запустить проверку `python -m tools.migrate_legacy --scriptfiles PATH`. Она не обращается к БД, не показывает bcrypt-хеши и не меняет файлы.
4. Установить совместимый драйвер вне репозитория: `python -m pip install mysql-connector-python`. Задать `TARKENSO_DB_HOST`, `TARKENSO_DB_PORT` (необязательно), `TARKENSO_DB_NAME`, `TARKENSO_DB_USER`, `TARKENSO_DB_PASSWORD`. Текстовые файлы с паролем **не коммитить**.
5. Выполнить `python -m tools.migrate_legacy --scriptfiles PATH --apply --confirm EMPTY_DATABASE`. Только явное `--apply` выполняет запись. Импорт в непустую БД запрещён. Данные сохраняются одним транзакционным commit; при любой ошибке выполняется rollback.
6. Сверить числа строк и отдельные контрольные суммы архивной копии; затем отдельно проверить Pawn MySQL-адаптер на тестовом сервере. **Не менять prod config.json до приёмки.**

### Ограничения

* Весь импорт — перенос **снимка**, не live-replication. Изменения после снятия копии не попадут в БД.
* Записи организаций с ID 1–3 импортируются как активные, ID 4 — как зарезервированная отключённая организация, даже если файла состава ещё нет.
* Система не переносит историю `ledger.log`, репорты, административные audit.log, старые чаты, объекты карты и прочие эфемерные данные. Хранить файловый архив отдельно.
* При наличии незавершённых `.tmp`, повреждённых файлов или конфликтующих членов организаций импорт **прерывается**, исправление вручную с аудитом первоисточника.
* Файлы аккаунтов `SIGNAL0317|1..5` сохраняют bcrypt-хеш без изменения. Для исторических `v1/v2` установка маркера выплат уборщика из `.clean` только фиксирует уже заработанную историю — не выдаёт деньги заново.
* `.ban` может быть выдан на ник без аккаунта, поэтому у таблицы bans нет внешнего ключа на accounts.
* Для соответствия реальной экономике защита дублей выплат должна переехать в транзакции сервера и использовать уникальные event-id. Этот SQL и импортер не включают переключение игрового хранения.
* Доступ и TLS к конкретному хостингу проверяются перед подключением; TLS-опции будущего Pawn-компонента и возможности MySQL провайдера требуется согласовать.

## TextDraw Studio, migration 012

Apply `migrations/012_tdstudio_projects.sql` once after 011, using MySQL 8.0.16+ and a migration account with CREATE ROUTINE. Runtime uses the existing R41 connection, EXECUTE on the four `tds_*` routines and CRUD on the two new tables. The routine security model is INVOKER. No existing game table is altered. See `docs/TEXTDRAW_STUDIO_STAGE2.md` for CP1251 transport, installation and testing.

TextDraw Studio stage 3.1 adds `migrations/015_tdstudio_groups.sql` after 012 (013/014 are reserved for LoadTest/LoadNet in current main). Apply once with the migration account, then grant the existing runtime user CRUD on `tdstudio_groups`/`tdstudio_group_members` and EXECUTE on `tds_save_v2`/`tds_load_v2`. It adds project-scoped groups, membership and `next_group_id`; format-1 records and original routines are preserved. No dependency on LoadTest/LoadNet migrations is introduced. See `docs/TEXTDRAW_STUDIO_STAGE31.md` for installation, compatibility, real MySQL checks and manual GTA acceptance.

Stage 3.3 adds `migrations/016_tdstudio_templates.sql` once after 015, using the same MySQL 8.0.16+ infrastructure. It creates only the four `tdstudio_template*` tables and six `tds_template_*` routines; old projects and 012/015 routines remain unchanged. The migration account needs DDL/CREATE ROUTINE; the existing runtime account needs CRUD on the new tables and EXECUTE on the six routines (SQL SECURITY INVOKER). Runtime does not need DDL privileges. Missing 016 disables library requests while 015 project persistence remains available. History is session memory and requires no schema. See `docs/TEXTDRAW_STUDIO_STAGE33.md` for limits, authorization, real R41 checks, restart and export results.

## Казна государства, migration 017

После 016 можно применить `migrations/017_treasury_core.sql` (MySQL 8.0.16+ / MariaDB 10.6+) с учётной записью миграций. Миграция создаёт **две таблицы** (`treasury_accounts` с балансом и всеми настройками в одной строке, `treasury_ledger` с историей операций) и атомарную процедуру `treasury_post`; баланс по умолчанию 0. При отсутствии 017 сервер продолжает обслуживать игроков, а казна остаётся недоступной. Для режимов с файловой авторизацией подключение казны отключено; в `TARKENSO_DB_PRIMARY` используется действующее подключение MySQL. До внедрения денежных механик казна **не** взаимодействует с балансами игроков и PayDay. Права подключения, протокол идемпотентных проводок, ограничения Pawn и проверки описаны в [`docs/TREASURY_CORE.md`](../docs/TREASURY_CORE.md).

## GOV-00, migration 018

После миграции 017 на тестовой БД выполните один раз `migrations/018_gov_atomic_transfers.sql`. Это независимая, атомарная и идемпотентная операция перевода денег между счётом игрока и единой казной; отдельная таблица `gov_transfers` хранит подтверждённые события. Никаких автоматических переводов и публичных команд нет. В файловом режиме система отключена, без миграции 018 — также отключена. Требования к правам MySQL, асинхронному Pawn API и порядок приёмочных проверок указаны в [`docs/GOV00_FINANCIAL_CORE.md`](../docs/GOV00_FINANCIAL_CORE.md). Важно: ранее применённую миграцию 017 не повторять.

## GOV-01, миграция 019

Следующий, неавтоматический этап: защищённый страховой резерв облигаций внутри единой казны. Новые поля `bond_fund_reserved`, `bond_fund_committed` и параметры страхования; защищённые списания в **обеих** процедурах `treasury_post` и `gov_transfer_post`; журнал `bond_fund_ledger`, резервирование гарантий `bond_fund_guarantees`. Миграция **019** применяется *один раз строго после 018*, только при остановленном тестовом сервере. На production до итоговой приёмки **не применять**. Полное описание: [`docs/GOV01_BOND_INSURANCE_FUND.md`](../docs/GOV01_BOND_INSURANCE_FUND.md).

## GOV-02, миграция 020

Реестр выпусков государственных облигаций, пустой реестр держателей, транзакционное одобрение с резервированием страхового фонда, открытие размещения и отмена **только непроданных** выпусков. Применять строго после 019, на остановленной тестовой среде; миграция 020 блокирует отдельную процедуру `bond_fund_commit`, заменяя её атомарным утверждением выпуска. **На рабочую БД до завершения всей финансовой системы не применять.** Спецификация: [`docs/GOV02_BOND_ISSUES.md`](../docs/GOV02_BOND_ISSUES.md).

## GOV-03, миграция 021

После GOV-02 (020) выполняется миграция **021** с реестром покупок,
требованиями инвесторов, защищённым расчётным резервом
`bond_payout_reserved`, страховыми начислениями и атомарным
получением выплат. Миграция заменяет процедуры `treasury_post` и
`gov_transfer_post`: обычные списания защищают **оба** резерва,
страховой и расчётный. Для получения игроком денег сервер проверяет
версию аккаунта, а офлайн-инвесторы сохраняют подтверждённое право
на средства в казначейском расчётном резерве. Автоматический обработчик
облигаций использует серверное UTC-время.

Все операции и ограничения: [`docs/GOV03_BOND_SETTLEMENT.md`](../docs/GOV03_BOND_SETTLEMENT.md).
Миграцию выполнять **один раз**, только на остановленной тестовой среде
после 020. **Не применять к рабочей БД до итоговой приёмки GOV-00—06.**

## GOV-04, миграция 022

Просроченные обязательства, частичное погашение долга из новых **реальных** поступлений казны, отдельный журнал раундов выплат, бюджетные статусы `NORMAL/STRESSED/DEFAULT/RECOVERY`, двухстороннее утверждение плана реструктуризации. Исходный номинал, процентная ставка, условия страхования и права инвесторов **не изменяются**. Применять только после 021 при остановленном тестовом сервере, **один раз**. На рабочей БД до итоговой приёмки GOV-00—06 **не применять**. Спецификация: [`docs/GOV04_DEBT_CRISIS.md`](../docs/GOV04_DEBT_CRISIS.md).

GOV-05 также расширяет `bond_fund_ledger` операцией
`TAX_EARMARK` и создаёт `government_bond_tax_earmarks`.
После отражения положительного `source='tax'` в казне 5% суммы
резервируется в фонде F без изменения общего баланса; повторные
отчисления запрещены уникальным ключом исходного налогового
события.

## GOV-05, миграция 023

Добавлена стандартная организация №5 «Министерство финансов» с четырьмя рангами и проверкой членства, автоматическая транзакционная сквозная нумерация эмиссий без года (`GOV-000001`, `GOV-000002`, далее без сброса при смене года и без повторного использования), процедуры создания проекта займа, проверки фракционных полномочий для подписания/мотивированного отклонения/открытия/отмены. Миграция также запрещает изменение публичного кода даже в состоянии DRAFT. Применять строго после 022 на остановленной тестовой среде, один раз. **Не применять в production до этапа GOV-06 и итоговой приёмки.** Описание: [`docs/GOV05_BOND_GOVERNANCE.md`](../docs/GOV05_BOND_GOVERNANCE.md).

## GOV-05.1 — миграция 025 после финансовой проверки GOV-06

`025_bond_application_revisions.sql` запускается **после 024** только
на изолированной MariaDB. Вводит `RETURNED` с сохраняемой причиной,
неизменяемый журнал возвратов, процедуры `gov_bond_official_return` и
`gov_bond_issue_resubmit`, а также переназначение часов размещения
на реальный SQL-переход `APPROVED → OFFERING`. Переопределяет две
основные финансовые процедуры как `SQL SECURITY DEFINER`, поэтому
необходимо использовать выделенного проверенного DBA и заново
проверить `DEFINER` и SQL-привилегии. Отдельный UAT:
`tests/gov05_revision_mysql_uat.py`. **Не применять к рабочей БД и
не сливать PR #94 до полного приёмочного испытания.**

## GOV-06 — миграция 024 и окончательная приёмка

Миграция `024_finance_assurance.sql` применяется только после 023, один
раз при остановленном тестовом сервере. Устанавливает неизменяемость
финансовых журналов, переводит хранимые процедуры на `SQL SECURITY DEFINER`
и вводит независимую процедуру `CALL gov_finance_assert_integrity()`.
Она сверяет единый баланс казны с журналами, резервы F/E/P, суммы
владения облигациями, покупки и зарегистрированные выплаты.

Полный перечень требований, ограничений SQL-привилегий, образец
распределения полномочий сотрудников Министерства финансов и чек-лист
финальной приёмки: [`docs/GOV06_SECURITY_ACCEPTANCE.md`](../docs/GOV06_SECURITY_ACCEPTANCE.md).

**Не применять в рабочей БД и не сливать PR #94 до итоговой приёмки.
GOV-06 не отменяет риск широких DML-прав основного игрового SQL-логина.**
