# TARKENSO — CI Performance & Profiling (Stage 1)

Проверка производительности состоит из **двух независимых блоков**: статического выявления горячих участков кода и **исполнения настоящего Pawn AMX на сервере open.mp**.

## 1. Pawn Complexity Guard

Команда:

```bash
python3 tools/check_pawn_complexity.py --output build/pawn_complexity.json
```

Использует общий лексический анализ Pawn: маскирует комментарии и строковые литералы, определяет функции и тела циклов с учётом вложенности скобок. Отслеживает горячие точки `OnPlayerUpdate`, `OnPlayerConnect`, `OnGameModeInit`, периодические `SetTimer/SetTimerEx` с **известным** интервалом до 1000 мс. Исследует обработчик и цепочку до двух непосредственных вызовов helpers.

| Код | Сигнал |
|---|---|
| `HOT_LOOP_IO` | Запросы MySQL, синхронные файлы или создание/удаление объектов/TextDraw внутри цикла, вызываемого горячим обработчиком |
| `NESTED_MASS_SCAN` | Вложенные циклы с обобщёнными признаками полного обхода игроков и игровых сущностей |
| `FAST_TIMER_LOOPS` | Два и более цикла в обработчике таймера с периодом до 250 мс |

Отчёт `pawn-complexity-report` содержит полный JSON; до 50 находок сопровождаются GitHub-аннотациями. Предупреждения **не блокируют CI**, поскольку число итераций и количество игроков сами по себе не доказывают деградацию тикрейта. `#if`, макросы, вызовы по строковым именам, условные ветки, runtime-измерение стоимости нативов и сложный граф вызовов пока не учитываются полноценно. Код `foreach` обрабатывается эвристически.

## 2. Реальный AMX Benchmark: алгоритмы судоходства

Используются **оригинальные** `ShipNotice_Distance` и `ShipNotice_TravelSeconds` из `gamemodes/includes/ship_notice.inc`. Один тестовый Pawn gamemode `tests/pawn/perf_ship_harness.pwn` запускается на официальном `omp-server` на `127.0.0.1`, без подключённых игроков, MySQL, плагинов и авторизации. Создаётся тестовый объект и заранее заданная одинаковая последовательность путевых точек. Измеряются `GetTickCount()` и контрольная сумма вычислений.

На **том же runner** сравниваются два AMX:
1. `origin/main` — исходный `ship_notice.inc` через `git show`;
2. `HEAD` текущего PR — этот же include из рабочей копии.

Оба AMX компилируются одним `pawncc`; общий хост и тестовая сцена одинаковы. По каждой функции предусмотрены прогрев, **7 замеров**, медиана и медианное абсолютное отклонение (MAD). Benchmark компилируется независимо от основной production сборки.

```bash
python3 tools/run_pawn_benchmark.py --server /path/to/open.mp-sdk \
  --baseline-ref origin/main --output build
```

JSON-артефакт `pawn-performance-report` содержит `pawn_perf_bench.json`, журналы компиляции и запуска.

### Логика регрессии

CI сигнализирует о замедлении, если одновременно:

- медиана новой версии **не менее чем на 20%** выше медианы базовой;
- замедление составляет **не менее 3 мс**;
- базовая медиана — не менее 3 мс, измерения достаточно стабильны (MAD не превышает максимум из 3 мс и 15% медианы);
- совпадают контрольные суммы (при изменении алгоритма сравнение помечается как несопоставимое).

Результат `regression` пока создаёт только **warning**, поскольку GitHub-hosted runner имеет переменную производительность. Невозможность скомпилировать или запустить AMX, отсутствие базового файла, неполные измерения/неверная контрольная сумма **блокируют шаг**, а не маскируются «нулевой регрессией».

**Важно:** `GetTickCount` измеряет прошедшее время, не фактическую загрузку CPU; изолированный бенчмарк не оценивает реальный онлайн 500 игроков, тикрейт и влияние MySQL. Отдельный нагрузочный тест TARKENSO и профилировщик авторизации сохраняются.

## Что дальше

Первыми расширениями могут стать тестируемые чистые процедуры из подсистем PayDay, бизнеса и поиска сущностей, а затем отдельный runtime stress-test с реальными игровыми callback и замерами распределения задержек серверных тиков. Порог 20% пока оставляем консультативным; блокирующим его можно делать только после стабильных измерений и ручного триажа.

CI Build запускает `Pawn Complexity Guard` до загрузки SDK, а парное сравнение AMX — после получения SDK и `git fetch origin main`. Отчёты хранятся 7 дней.
