# TARKENSO /bonds — игровой интерфейс инвестора

Рабочий интерфейс для граждан, добавлен в накопительный **PR #94** поверх
GOV-00—GOV-03. Приёмка всей системы — после GOV-06, раньше миграции
на рабочей базе не применять.

## Открытие

В игре введите **/bonds**. Команда доступна авторизованному игроку
в любом месте (до отдельного здания казначейства). Требуется работающий
MySQL-primary, миграции 017—021 и готовый GOV-03. В файловом режиме
команда корректно сообщает о недоступности.

Используются стандартные open.mp диалоги с зарезервированными ID
**6700—6710**. Отдельный TextDraw и клиентские файлы не нужны.
Диалоги учитываются в общей проверке коллизий ID в CI.

## Оформление (табличные диалоги)

В двух главных реестрах применён `DIALOG_STYLE_TABLIST_HEADERS`, а не
`DIALOG_STYLE_LIST`. ID остаются прежними: **6701** для доступных
госзаймов, **6704** для портфеля. Вкладка использует настоящие табуляции
`\\t`; первая строка — заголовки, на которые нельзя нажать.

**Реестр госзаймов:** `Выпуск | Номинал | Доходность | Доступно`.
Доходность отображается как процент за весь срок (`1.00%`, а не `100 bp`),
наличие — в штуках.

**Портфель:** `Выпуск | Количество | Номинал | К выплате`.
Суммы оформлены единым светлым цветом, независимо от знака и статуса.

**Цветовая система:** все тексты и значения внутри диалогов `/bonds`
и `/bondgov` используют один нейтральный светлый цвет `{E8EDF3}`.
Это устраняет пёстрые строки в списках, карточках и подтверждениях.
Типизированные статусы, предупреждения, сумма и лимиты остаются
написанными словами; их смысл не должен зависеть от цвета. Штатная
подсветка выбранной строки клиентом SA-MP/open.mp сохраняется.
Общесерверные информационные сообщения не относятся к палитре меню.

Постраничный список рассчитан на 10 выпусков. Навигация `Следующая
страница`, `Предыдущая страница`, `Вернуться в меню` занимает
отдельные строки таблицы, но **никогда не считается записью выпуска**.
При отсутствии записей отображается информационная строка, не
привязанная к ID облигации. Это учитывается в обработке `listitem`;
заголовок `TABLIST_HEADERS` не входит в нумерацию строк.

Карточки выбранных выпусков, подтверждение покупки, сведения о долге
и получение выплат оформлены в том же стиле. Статусы
`DEFAULTED` / `OVERDUE` и `SETTLED` различаются словесно, не цветом.

## Русские статусы обязательств в портфеле

В карточке позиции инвестора поле «Статус долга» выводится по-русски:
`NOT_DUE` → **«Срок не наступил»**, `DUE` → **«К погашению»**,
`PARTIALLY_PAID` → **«Частично погашен»**,
`OVERDUE` → **«Просрочен»**, `DEFAULTED` → **«Дефолт»**,
`RESTRUCTURED` → **«Реструктурирован»**,
`SETTLED` → **«Погашен полностью»**. Статусы показаны
единым цветом и различаются по русским названиям.
Технические значения в MySQL и вся финансовая логика остаются прежними.

### Купонные уведомления при PayDay

После каждого подтверждённого начисления MySQL игрок видит рядом с
основным PayDay (EXP) строки с доходом по выпуску GOV и общей суммой.
В сообщении не больше трёх кодов, при большем числе позиций
выводится общий итог. Нулевое начисление не показывается. Офлайн
начисления выводятся при следующем входе. Сообщение не зачисляет
купон на кошелёк: `/bonds → Купонный счёт → Получить` остаётся
отдельным ручным действием. Миграция 027 обязательна.

## Пошаговая покупка любого допустимого количества облигаций

1. Введите `/bonds`, откройте **«Доступные государственные займы»**.
2. Выберите выпуск в таблице `Выпуск | Номинал | Доходность | Доступно`.
3. Сервер повторно читает условия из MySQL, число уже имеющихся у вас
   облигаций **этой серии**, их остаток и лимит казны на одну операцию.
4. Нажмите **«Купить»**. В `DIALOG_STYLE_INPUT` появится:
   **«Введите количество облигаций от 1 до N»**.
   Если `N=0`, покупка недоступна.
5. Введите целое число. Отрицательные значения, знаки, пробелы,
   дробные числа, переполнение и количество больше `N` отклоняются.
6. Подтвердите покупку в `DIALOG_STYLE_MSGBOX` — указаны выпуск,
   количество, номинал одной бумаги, **общая стоимость** и ваш баланс.
7. Сервер выполняет **одну атомарную SQL-транзакцию** на весь объём.
   Ответ об успешной покупке `k` шт. показывается только после коммита.

### Формула доступного количества

Для выбранного кода `GOV-xxxxxx`:

`C = floor(общее_количество_выпуска / 5)` — строго не более **20%**
выпуска на одного игрока.

`U = max(0, C − уже_принадлежит_игроку_по_этому_коду)`

`N = max(0, min(U, непроданный_остаток,
floor(баланс_кошелька / номинал),
floor(лимит_одной_транзакции_казны / номинал)))`.

Каждый код имеет **независимый лимит**. Владение 20% выпуска
`GOV-000001` не запрещает приобретать до 20% `GOV-000003`.
SQL хранит позиции по ключу `(issue_id,account_id)` и объединяет
последующие покупки одной серии в её суммарное количество.

Диалог показывает предварительный расчёт. При окончательном выполнении
`gov_bond_buy` под блокировками MySQL заново проверяет статус размещения,
денежный остаток, доступные бумаги, реальное владение и предел 20%.
Из-за конкурентной покупки другим игроком `N` может измениться —
в таком случае **вся** транзакция откатывается, частичного списания нет.
Уникальный `event_key` предотвращает повторное проведение одной операции.

У выпуска с количеством меньше пяти бумаг строгое ограничение
даёт `C=0`. Поэтому **новый государственный выпуск содержит минимум
5 облигаций**, а старые тестовые серии из 1–4 бумаг купить нельзя.

При недостатке денег или превышении лимита MySQL выдаёт
подтверждённый `ROLLBACK`, а игрок получает понятный отказ.
**Неудача покупки не должна отключать весь сервер**:
для таких бизнес-отказов добавлен отдельный обработчик ошибки
`BondSettlement_OnError` с безопасным снятием блокировки кошелька.
Неизвестные сетевые результаты по-прежнему обрабатываются fail-closed,
так как списание могло успеть подтвердиться без ответа клиенту.

Повторная отправка того же диалога не создаёт новую покупку:
подтверждение потребляется однократно до запуска операции.
Повтор в SQL с тем же `event_key` также идемпотентен.

## Портфель

`/bonds` → **«Мой инвестиционный портфель»**.

Показываются из реестра:
- Код выпуска.
- Количество принадлежащих игроку бумаг.
- Номинал одной бумаги, ставка за срок.
- Состояние долга (включая дефолт).
- Остаток основного государственного долга.
- Доступная подтверждённая выплата, если она есть.

В каждой позиции можно выбрать **«Получить»** и подтвердить
перевод заблокированной в казне суммы на собственный кошелёк.
При заполнении кошелька перевод ограничен оставшимся до
`ACCOUNT_MAX_MONEY` пространством; не полученная часть сохраняется
в escrow и доступна позднее. Чужие выплаты получить нельзя:
SQL `gov_bond_claim_collect` строго проверяет owner account.

Если сервер начислил выплаты, пока игрок отсутствовал, они будут
отображены после следующего входа без потери средств.
Список и карточка считываются из SQL на каждом открытии,
не из несинхронизированного массива Pawn.

## Важные ограничения

- Команда доступна только для реальных **OFFERING** выпусков,
  которые уже созданы и утверждены в GOV-02. Без них список пуст.
  Меню **не создаёт фиктивные демонстрационные облигации**.
- Министр и заместитель управляют размещением через `/bondgov` (GOV-05).
- Один подтверждённый заказ приобретает от 1 до N бумаг **одной серии**;
  разные серии приобретаются отдельными заказами.
- Для неоплаченного остатка после дефолта GOV-04 реализует отдельную
  процедуру дальнейшего погашения и/или реструктуризации.
- Капитализация страхового фонда и выпуск бумаг **не создают деньги**.
- Не применять миграции 018—021 к production до общей приёмки GOV-06.

## Контрольные проверки

1. `/bonds` до авторизации / без MySQL — отказ без списания.
2. Нет OFFERING → пустой список с работающей кнопкой «Назад».
3. Есть OFFERING → список, расчёт N и ввод количества.
4. Купить k шт. → `government_bond_orders` +1, `holdings.quantity` +k,
   кошелёк минус (номинал × k), казна плюс та же сумма, фонд плюс взнос.
5. Двойной ответ в диалоге → ровно один заказ; 0, N+1, abc → отказ.
6. Недостаток денег / распродажа / лимит владения → отказ,
   без изменения балансов и без отключения остальных игроков.
7. Два игрока берут последнюю бумагу → только один получает право.
8. `/bonds` → портфель, достоверное число бумаг, владельцы не смешиваются.
9. Погашение в отсутствие игрока → отображение escrow после возвращения.
10. Получение выплаты дважды → только один перевод; второй — отказ.
11. Кошелёк близок к лимиту → частичное получение без переполнения.
12. Переподключение / поздний MySQL callback → нельзя применить
    денежную операцию к другой сессии.
13. Проверка CI не обнаруживает пересечений диалоговых ID 6700—6707.
14. Два GOV-кода в портфеле и докупка одной серии проверяются отдельно.
15. Pawn компилируется без ошибок и предупреждений,
    MariaDB GOV-00—03 UAT проходит в изолированной среде.

Финансовые показатели включают также отчисления в страховой фонд из
реальных налоговых поступлений по ставке, заданной казной. Такие
отчисления блокируются внутри имеющегося баланса, не создавая деньги.

## GOV-05 — публичная отчётность

Четвёртый пункт гражданского меню `/bonds` — **«Публичная отчётность казны»**. Открывает только читающий SQL-отчёт о балансе казны, страховом резерве F, принятом обеспечении E, защищённом резерве выплат P, сумме необеспеченной задолженности, количестве и состоянии выпусков. Отчёт не даёт игроку права создавать эмиссии. Список должностей и процедура их выдачи: [`GOV05_BOND_GOVERNANCE.md`](GOV05_BOND_GOVERNANCE.md).

Для сотрудников Минфина: создание проекта через `/bondgov` формирует
уведомление в чат организации. Заместитель/министр отдельно утверждает
выпуск через карточку `/bondgov` (свою заявку подписывать можно).
В таблице выпусков показываются код, заявитель, количество, номинал и
статус; в карточке руководитель может «Подписать» или «Отклонить».
При отклонении вводится причина, которая сохраняется и видна автору.

## UAT 28.10.2026 — устранение ошибок покупки и кириллицы

- `GOV-000001` (20 шт.): при покупке 4 шт. достигается персональный
  предел 20%, далее карточка отображает причину отказа и не приглашает
  нажать «Купить». Отдельные сообщения предусмотрены для нулевого
  остатка, недостатка средств, лимита казначейской операции и закрытого
  размещения. Проверка в MySQL остаётся окончательной.
- Игровые Pawn-строки и `inputtext` обрабатываются в CP1251. Сессия
  MySQL R41 `mysql_connect_file` переводится в `cp1251` через
  `mysql_set_charset` **до любых запросов**, чтобы сервер преобразовывал
  строки в `utf8mb4` таблиц и возвращал игровой текст в CP1251.
- Уже существующие строки `title/purpose`, введённые до изменения,
  автоматически **не переписываются**. Для восстановления конкретных
  записей сначала нужно изучить `HEX(title)`, `HEX(purpose)`, создать
  backup, затем разработать адресную процедуру с соблюдением триггеров
  неизменности параметров выпущенного займа. Финансовые суммы не трогать.
- CI проверяет соединение CP1251 и сохранение русских символов в
  изолированной временной таблице `utf8mb4` (без изменения выпусков).
