# TARKENSO TextDraw Studio — этап 2

Интерактивное позиционирование мышью/клавиатурой описано в
[дополнении 2.1](TEXTDRAW_STUDIO_STAGE21.md): управление, архитектура и результаты проверок.

## Установка

1. Нужны существующий MySQL R41, тот же `mysql.ini` и MySQL **8.0.16+**.
   Применить миграции 001..011, если их ещё нет, затем один раз импортировать
   [`012_tdstudio_projects.sql`](../db/migrations/012_tdstudio_projects.sql).
   Использовать импорт SQL-файла, включая `DELIMITER` и все четыре процедуры.
   Применение к рабочей БД в этой задаче не выполнялось.
2. Учётной записи миграций нужны права создания таблиц/процедур. Рабочей записи
   сервера нужны `EXECUTE` для `tds_save`, `tds_load`, `tds_list`, `tds_delete` и
   SELECT/INSERT/UPDATE/DELETE для новых таблиц (`SQL SECURITY INVOKER`).
   Второго подключения и новых игровых плагинов нет.
3. Установить новый `compiled.amx`. Проверка версии 12 выполняется асинхронно при
   запуске редактора. Если миграции/БД нет, сохранение и загрузка отключены с
   сообщением; создание интерфейса в памяти и экспорт остаются доступны.
4. Основатель входит через существующую авторизацию и включает `/aduty`, затем
   `/tdstudio`. Коллегам доступ отдельно выдаётся `/tdgrant ID 1`, отзывается
   `/tdgrant ID 0`. Временные права после переподключения выдаются заново.

## Главное меню

Создать; открыть; сохранить; сохранить как новый; переименовать; удалить из БД;
экспортировать; редактировать интерфейс; параметры проекта; закрыть редактор.

В заголовке показываются имя и ID проекта, `*` означает несохранённые изменения.
Новый проект получает ID после подтверждённого сохранения. Имя — 1..32 символа,
без путей и файловых спецсимволов, с буквой или цифрой. В параметрах доступны
описание до 128 символов, тип `TextDraw`/`PlayerTextDraw`, автор, ревизия и даты UTC.
Меняется тип итогового экспорта; сам редактор всегда рисует личный предпросмотр.

Список проектов загружается только по явному открытию, по 20 записей на странице.
Разработчик видит свои проекты; подтверждённый основатель имеет право доступа ко
всем. Переименование/описание/тип сначала меняются в памяти и требуют сохранения.
«Сохранить как новый» создаёт проект текущего автора и переключает редактор на копию.
Удаление из БД требует подтверждения, удаляет элементы каскадно и очищает текущий
проект только после ответа БД. Несохранённый черновик удаляется закрытием.

При переключении/создании другого проекта и закрытии редактор предупреждает о
несохранённых изменениях. Во время запроса/экспорта редактирование заблокировано;
закрытие разрешено. Уже отправленный запрос сохранения может успеть записаться
после закрытия — это не означает, что ответ будет применён к новой сессии.

## Архитектура

Первый этап сохранён; добавлены три модуля:

| Модуль | Ответственность |
| --- | --- |
| `tdstudio_codec.inc` | проверка всего проекта, порядок, версия, HEX и ограниченный JSON-транспорт |
| `tdstudio_db.inc` | существующий `gDBPrimary`, асинхронные задания, загрузка и ответы БД |
| `tdstudio_export.inc` | проверенный генератор реального Pawn, безопасные файлы и инструкции |

Расширены модель/ядро/действия/UI. Рендерер выделяет функцию отрисовки отдельной
модели, чтобы сначала выделить ресурсы для загрузки, а затем заменить старый
интерфейс. При недостатке PlayerTextDraw старый проект сохраняется. Исправлен
порядок после удаления/добавления в свободный слот: `tdOrder` отделён от индекса
массива, создание/загрузка/экспорт используют один порядок. Пересборка нужна при
добавлении элемента для порядка native-хэндлов; смещения и свойства обновляют
только выбранный хэндл, как на этапе 1.

Новые команды не добавлялись: функции находятся в `/tdstudio`; `/tdgrant` сохранён.
Зарезервированные диалоги: **7100..7117**. Прежние обработчики сортировки и её
клики сохранены. Из общего MySQL error-handler перехватываются только callbacks
редактора; его SQL-ошибка не отключает БД всего мода и не выкидывает других игроков.

## Схема и атомарность

`tdstudio_projects`: ID, имя/описание CP1251, creator FK accounts, тип интерфейса,
версия формата, ревизия, следующий ID элемента, даты создания/изменения.

`tdstudio_elements`: project FK с CASCADE, ID элемента, ordinal и draw_order,
все 27 скалярных полей модели и CP1251-текст. Индексы обеспечивают уникальность
ID, ordinal и порядка внутри проекта. Координаты хранятся числовыми DOUBLE;
транспорт передаёт девять десятичных знаков. Сравнение Float в тестах — с допуском
`1e-6`, остальные поля и CP1251-текст сравниваются точно.

Один `mysql_tquery` вызывает параметризованную процедуру `tds_save`. Внутри одного
CALL выполняются START TRANSACTION, блокировка проекта FOR UPDATE, проверка
автора/прав и ожидаемой ревизии, замена метаданных/элементов и COMMIT. Исключение
вызывает ROLLBACK и `ok=0`; только ответ `ok=1` с подходящими метаданными снимает
dirty. Ревизия предотвращает потерю изменений при конкурирующих авторах.
Дата создания и автор при обычном сохранении не меняются. Лимит — 100 проектов
на автора, до 64 элементов, восемь сессий и восемь незавершённых DB-заданий.

R41 **не предоставляет client-side prepared statement / bind API**. Поэтому
параметризация реализована типизированными параметрами хранимых процедур и
статическими SQL-операциями внутри них. В тексте CALL строки передаются только
как проверенные HEX-литералы, числа — как серверные целые. Пользовательский текст
не включается в SQL как SQL-синтаксис. Это не заявление об использовании protocol
prepared statements. JSON — ограниченный транспорт из памяти в процедуру;
постоянное хранение нормализовано в двух таблицах, не в JSON-файле/одном blob.
CP1251-столбцы и HEX исключают зависимость от charset соединения и sql_mode.

Загрузка — один согласованный SELECT с LEFT JOIN внутри `tds_load`: метаданные,
количество и элементы в порядке ordinal. Сначала проверяются версия, все поля,
ID, уникальность, длины и доступ, затем выделяются временные хэндлы. Только
полностью успешная загрузка заменяет действующий проект. Неизвестная версия,
некорректные данные, отсутствие прав или отказ ресурсов сохраняют текущий проект.

## Асинхронная безопасность

Задание хранит ID аккаунта, токен подключения, уникальную аренду сессии, номер
операции и ожидаемую ревизию. Повторный запрос в той же сессии не ставится в очередь.
Закрытие/отключение не переиспользуют контекст запроса: устаревший callback
освобождает своё задание и не меняет новую сессию. Права повторно проверяются в
callback. Авторизация запроса БД относится к моменту его отправки.

За 30 секунд без ответа снимается busy, но флаг dirty не сбрасывается. Исход операции
объявляется неизвестным: перед повтором нужно проверить список проектов. Поздний
ответ не помечает текущий проект сохранённым. Это важно при разрыве сети после
COMMIT: отсутствие ответа не доказывает отсутствие записи. Автоматического повтора
создания копии нет. Слот задания остаётся занят до позднего ответа/ошибки, а повторный DB-запрос в той же аренде сессии не отправляется. Это ограничивает также очередь внутри плагина, а не только массив Pawn. Редактирование не вызывает SQL-запросов.

## Экспорт и подключение

Нативные файловые функции open.mp ограничены `scriptfiles`, поэтому результат:

`scriptfiles/tdstudio_exports/TD_<slug>_<nonce>.inc`

Рядом — одноимённая `.txt` инструкция. Каталог — доверенная настройка сборки
`TDS_EXPORT_DIR`, а не ввод игрока. ASCII-префикс основан на названии; занятые имена
`.inc`/`.txt`/`.tmp` пропускаются. Незавершённый файл удаляется при закрытии/ошибке.
Готовый файл публикуется переименованием временного. Сторонние файлы не перезаписываются.
Экспорт ограничен восемью элементами за тик монитора, чтобы не записывать весь
максимальный проект одним длинным циклом. Пока экспорт выполняется, снимок заморожен.

Результат включает переменные, `Create`, `Show`, `Hide`, `Destroy`, `Hit` и
обработку частичного отказа создания. Персональные массивы имеют `[MAX_PLAYERS]`;
вызовы проверяют playerid и флаг создания. `Hit` возвращает исходный ID элемента,
или -1 для стороннего хэндла. Генератор не добавляет свои глобальные callbacks:
подключение в существующие события выполняется по инструкции с сохранением других
обработчиков. SelectTextDraw включается перед Show, если интерфейс кликабельный.

Файл записывается **сырыми байтами CP1251**, не UTF-8-конвертацией `fwrite`.
Кавычки/обратные слеши экранируются, `%` остаётся данными благодаря формату `%s`
в Create. Русский текст и существующий rustext не изменяются.

Для текущего UTF-8 репозитория: декодировать `.inc` из CP1251 в UTF-8, поместить в
`gamemodes/includes`, включить после open.mp; штатная сборка переведёт его обратно
в CP1251. Для прямого подключения в CP1251-исходник конвертация не нужна.
Реальные примеры этого генератора, сохранённые в UTF-8 для Git:
[`tdstudio_player_example.inc`](examples/tdstudio_player_example.inc) и
[`tdstudio_global_example.inc`](examples/tdstudio_global_example.inc).

## Проверки и границы

Результаты и воспроизводимый запуск: [TEXTDRAW_STUDIO_STAGE2_VALIDATION.md](TEXTDRAW_STUDIO_STAGE2_VALIDATION.md).
Новая функциональность проверена с настоящими MySQL 8/R41 и Pawn runtime, но
игроки/нативный UI в сценарии заменены двойниками. Реальный GTA-клиент, визуальное
совпадение после загрузки и сортировка после работы с редактором требуют ручной
приёмки. Новый процесс open.mp действительно повторно загрузил проект из БД;
рестарт самого MySQL и сетевой обрыв непосредственно во время COMMIT не проверялись.

Третий этап не реализован. После ручной приёмки: Undo/Redo, выделение/группировка,
управление слоями, шаблоны и постоянная отдельная роль разработчика.
