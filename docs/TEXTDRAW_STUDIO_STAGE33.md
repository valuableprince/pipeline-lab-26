## Управление

В главном `/tdstudio` и в меню редактирования добавлены **«История действий»**
и **«Библиотека шаблонов»**. Существующие строки меню/индексы сохранены,
новые пункты добавлены в конец. Команды `/tdstudio` и `/tdgrant` остаются прежними.

### Undo / Redo

В обычном режиме холста доступны две дополнительные кнопки **UNDO / REDO**
справа под строкой статуса. Доступная кнопка активна, недоступная серая и
неперехватываемая. При поддельном клике сервер дополнительно проверяет состояние.
Кнопки скрыты в preview и во время клавиатурной операции.

«История действий» позволяет отменить/повторить действие, посмотреть до 20
последних операций и очистить историю **с подтверждением**. `[+]` означает
применённую запись, `[-]` — отменённую. Back возвращает в меню проекта.
Очистка не меняет проект и не сбрасывает контрольную точку сохранения.
Новое реальное изменение после Undo удаляет Redo-ветку; открытие меню,
перевыделение и изменение Grid-настроек её не удаляют.

Клавиатурные move/resize/scale работают как прежде: игровые действия направлений,
SPRINT (обычно Space) — шаг, CROUCH (обычно C) — ось resize/scale,
SECONDARY_ATTACK/YES (обычно Enter/Y) — подтвердить, NO (обычно N) или
`/tdstudio` — отменить незавершённую операцию. Это действия GTA, а не физические
keycodes. Ctrl+Z/Ctrl+Y не заявляются. Глобальная история доступна после завершения
или отмены локальной операции; удержание клавиши не создаёт отдельные записи.

### Создание шаблона

1. Выделить элемент, несколько элементов или группу.
2. «Библиотека шаблонов → Сохранить выделение как шаблон».
3. Ввести название 1..32 символа, выбрать категорию, описание до 128 символов
   (можно пустое), личный/общий доступ и подтвердить сохранение.
4. Дождаться ответа MySQL. Ошибка/timeout не выдаёт ложного успеха.

Категории: кнопки, панели, HUD, текстовые блоки, логотипы, прочее.
Стабильные числовые category ID допускают расширение до 65535; новые названия
можно добавлять в каталог без изменения формата элементов/таблиц.
Общий шаблон публикует только подтверждённый основатель, личный — любой
разработчик с разрешённым доступом. Лимит — 100 шаблонов на создателя.

### Использование и управление библиотекой

«Просмотреть / вставить шаблон» → категория (или все) → страница → шаблон.
На странице максимум 20 записей; следующие/предыдущие страницы загружаются
отдельно. Детали показывают автора, доступ, категорию, ревизию, даты и описание.
Библиотека доступна без активного проекта; вставка требует открытого проекта.

Доступны вставка, переименование, изменение описания и удаление с подтверждением.
Чужой общий шаблон можно использовать, но редактировать/удалять его может только
создатель или уполномоченный основатель. Основатель также управляет чужими личными.
Публикация/правка библиотеки не являются изменениями текущего проекта и не создают
Undo-записей. Уже вставленные копии не меняются при переименовании/удалении шаблона.

Размещение при вставке:

| Вариант | Значение |
| --- | --- |
| Центр экрана | общий прямоугольник центрируется в виртуальных 320/240; центр точный и при включённом Snap |
| X/Y | левый верх общего прямоугольника компонента |
| От активного элемента | вводимый вектор относительно его TextDraw-якоря |

Для последних двух вариантов Snap округляет одну общую точку, а не каждого
участника. После вставки новые элементы выделены для дальнейшего редактирования.
Вставка — **одна** операция Undo, даже для 64 элементов и нескольких групп.
Последующие move/scale/свойства/удаления работают обычными инструментами.

## Архитектура истории

`tdstudio_history.inc` содержит кольцевой журнал и checkpoint;
`tdstudio_history_ui.inc` — меню. Общий `tdstudio_state.inc` валидирует и атомарно
устанавливает целое логическое состояние; его используют история и шаблоны.
Прежний DB-loader переиспользует этот же единственный staging-буфер через aliases,
а чтение/кодирование наборов элементов выделено в общие функции.

Глубина — **20 завершённых операций** на сессию. 21 состояние кольца разделяет
соседние концы операций: before следующей операции совпадает с after предыдущей.
Для каждого перехода сохраняются тип и понятная подпись. Состояние содержит
все сохраняемые свойства элементов, состав/имена групп, порядок слоёв, имя,
описание и тип интерфейса проекта. Элементы и группы канонизированы по своим
**логическим ID**; физический слот массива не является идентификатором объекта.

В снимках нет PlayerTextDraw/toolbar/grid-хэндлов, playerid, session lease,
MySQL-соединения или cookie задания. Строки — исходные CP1251-байты, упакованные
по четыре на Pawn cell. Неиспользуемые места нормализованы в нули; сравнение
состояний не зависит от повторного использования физических слотов.

| Поддерживаемые действия | Единица истории |
| --- | --- |
| создание, удаление, дублирование | целый элемент и сопутствующее изменение групп/слоёв |
| текст, цвет, alpha, font, align, Box/background/outline/shadow, proportional/selectable, TXD, preview/rotation/zoom/vehicle colours | завершённое применение свойства |
| точные координаты/размеры/LetterSize, Snap-сдвиг | завершённая операция |
| клавиатурные move/resize/scale, в том числе группа | одно подтверждение для всего набора |
| align, distribute, screen placement | весь набор целиком |
| четыре операции слоёв | один переход порядка |
| создание/переименование/состав/расформирование групп | вся логическая операция |
| вставка шаблона | весь компонент, включая группы и порядок |
| параметры проекта | имя, описание, Global/Player тип |

Локальный снимок `gTDSOrigin` этапа 3.2 сохранён. До подтверждения он обслуживает
live-предпросмотр/отмену; глобальный снимок создаётся только на подтверждении
фактического изменения. При локальной отмене и при неизменённом результате
история не меняется. Ни SQL, ни снимков истории на кадрах нет.

### Восстановление и ID

Undo/Redo проверяет сессию, авторизацию, доступ к проекту, отсутствие busy/live
операции, границы курсора/тип записи и весь декодированный набор. Проверяются
числа/строки, уникальные ID/слои, членство, непустые группы и лимиты.

Если состав/порядок неизменны и старые хэндлы валидны, устанавливаются только
изменённые строки и переиспользуются прежние хэндлы. Имя/описание/группы не
создают новых TextDraw. Если нужен другой состав/слои или ремонт пропавшего
хэндла, сначала готовится **полный скрытый набор** в порядке `tdOrder`.
При отказе уничтожаются только временные хэндлы; старая модель, выделение,
dirty и курсор истории остаются. Курсор меняется только после успешного commit.

После структурной замены выделение сохраняется по существующим logical IDs;
если активный объект исчез, выбирается существующий. Само выделение не является
историей и не навязывает пользователю старый выбор. Логические группы, их ID,
имена и членство восстанавливаются точно.

`tsNextId` и `tsNextGroupId` — монотонные high-water counters, они не откатываются.
Удалённый/отменённый ID, включая ID в Redo-ветке, не переиспользуется при новом
создании. Redo восстанавливает прежние logical IDs. При исчерпании диапазона
новые объекты отклоняются до изменения модели.

При переключении проекта/закрытии/reset/shutdown журнал и checkpoint обнуляются,
слот сессии освобождается. При ветвлении неиспользуемая Redo-часть также стирается.
Резерв статического AMX-пула остаётся до выгрузки мода; динамических выделений
истории и незакрываемых heap-объектов нет.

### Checkpoint и MySQL

После подтверждённого save/load сохраняется отдельный канонический checkpoint.
Dirty определяется сравнением фактического содержимого с ним, а не курсором
истории или фактом вызова Undo. Checkpoint продолжает работать, когда нужная
операция уже вытеснена из кольца или история очищена.

Транзакция БД, ID проекта, автор, ревизия/даты и high-water counters не являются
отменяемым содержимым. Undo не откатывает уже завершённый COMMIT в БД; последующее
«Сохранить» записывает текущее подтверждённое состояние с прежней CAS-защитой.
Неизменность содержимого при выросшем allocator-counter не делает проект dirty.
Новый несохранённый проект остаётся черновиком до настоящего сохранения.

Проверены save после Undo, save после Redo, Undo после save, возврат к сохранённому
состоянию, Save As и load другого проекта. Во время SQL-задания или файлового
экспорта Undo/Redo недоступны. Ошибка БД не перемещает checkpoint.

### Верхняя граница памяти

При Pawn cell = 4 байта, `TDS_ELEMENTS=64`, `TDS_GROUPS=16`, `TDS_SESSIONS=8`:

| Часть | Расчёт | Байты |
| --- | --- | ---: |
| один элемент | 27 wire-скаляров + group ID + 32 packed cells текста | 240 |
| одна группа | ID + 9 packed cells имени | 40 |
| метаданные | interface + 9 cells имени + 33 cells описания | 172 |
| один образ | 64×60 + 16×10 + 43 = **4043 cells** | **16 172** |
| кольца восьми сессий | 8×21×4043×4 | 2 716 896 |
| checkpoints | 8×4043×4 | 129 376 |
| подписи, типы и курсоры/флаги | 8×(21×65+5)×4 | 43 840 |
| общий рабочий образ | 4043×4 | 16 172 |
| **вся история** | сумма, независимо от числа действий сверх лимита | **2 906 284 (≈2.77 МиБ)** |

Без упаковки образ занимал бы 10 691 cells; 21 образ × 8 — 7 184 352 байта
ещё до checkpoint/подписей. Отдельные before/after для всех 20 операций стоили
бы ещё больше. Выбранный ограниченный пул хранит необходимые конечные состояния
без сложности динамического allocator или журнала с непредсказуемым размером.
Полный raw staging — 42 112 байт, он заменяет прежний DB load-buffer, а не
дублирует его. Ещё один такой общий буфер компонента нужен для remap при вставке;
это один компонент на выполнение, не 64 элемента библиотеки на каждого игрока.

## Модель шаблонов и миграция 016

`tdstudio_templates.inc` содержит capture, валидацию, remap/вставку и адаптер
к общей очереди; `tdstudio_templates_ui.inc` — категории, wizard и управление.
**Схема проекта остаётся формата 2. `E_TDS_ELEMENT`, 012 и 015 не менялись.**

Новая миграция: [016_tdstudio_templates.sql](../db/migrations/016_tdstudio_templates.sql).
Перед выбором номера проверены main и база: 013/014 заняты LoadTest/LoadNet,
015 — группами. 016 свободен. Миграция не ALTER/DROP старые игровые/проектные
таблицы и не заменяет их процедуры. Реальный тест сравнивает все строки четырёх
старых проектных таблиц до/после 016.

| Таблица | Содержание |
| --- | --- |
| `tdstudio_templates` | ID, название/описание CP1251, category, visibility, creator ID, даты, ревизия, format=2, next IDs, исходная опора |
| `tdstudio_template_elements` | полный прежний набор свойств, stable source IDs, ordinal и относительный порядок слоёв |
| `tdstudio_template_groups` | ID/имя группы в компоненте |
| `tdstudio_template_members` | одно членство элемента; состав связывается составными FK |

PK, уникальные ordinal/order/имена групп, индексы owner/category и shared/category,
CHECK и FK/CASCADE защищают структуру. Шесть новых typed routines: save, list,
info, load, update, delete. Runtime использует **то же** R41-соединение/пул заданий,
lease/token/account cookies, timeout и общий перехват ошибок. Новых зависимостей нет.

R41 не предоставляет bind/prepared API: как в этапе 2, CALL использует типизированные
параметры процедур, числа и проверенные HEX-литералы. Ни одна пользовательская строка
не вставляется в SQL неэкранированной. CP1251 не зависит от charset соединения.
Ограничены строки, JSON 48 000/4096 символов, число элементов/групп и запрос 110 000.

Сохранение нового шаблона: проверка actor/publication/quota, START TRANSACTION,
lock строки аккаунта для квоты, metadata → elements → groups → membership,
проверка общей опоры → COMMIT. Ошибка на позднем элементе/группе или опоре
откатывает **все четыре сущности**. Изменение имени/описания и удаление используют
владельца/привилегию и ожидаемую ревизию; проигравший CAS не сообщает успех.

Для правки библиотеки учитывается creator/account ID, а не ник. Личные читают
создатель/основатель; общие также другие разрешённые разработчики. Правила повторены
в Pawn и SQL. Дополнительно закрыт случай сохранения доступа к истории чужого
проекта после потери founder-привилегии при оставшемся обычном editor grant.

### Координаты, группы и вставка

Компонент хранит неизменённые исходные Float-свойства и общий origin его
ограничивающего прямоугольника. Относительные смещения вычисляются как
`sourcePosition − origin`; новые позиции — `placement + offset`.
Так сохраняется точность исходных данных, без многократной нормализации текста,
у которого origin может быть отрицательным из-за right/center alignment.
У каждого использования исходник читается заново и не изменяется вставкой.

Частичное выделение группы сохраняет только выбранных участников; пустые группы
не включаются. При вставке назначаются новые ID элементов/групп, состав переназначается,
элементы добавляются над существующими с сохранением внутреннего порядка.
Совпавшее имя группы получает детерминированный суффикс с новым ID и номером попытки,
с ограничением 32 символа и проверкой уникальности. Вложенных групп не добавлено.

До commit проверяются лимиты и диапазоны **всей** композиции; потом атомарный
StateApply готовит нужные хэндлы. При отказе нет частичных объектов, потреблённых
ID, изменённого старого интерфейса или новой Undo-записи. Старые элементы не меняются.
Один глобальный временный компонент и общий staging не пересекают async boundary:
между запросами хранится только выбранная метаинформация, а load/insert обрабатывается
целиком в одном защищённом callback. Все последующие операции с копиями обычные.

| G/H/I | 20 последовательных отмен/повторов, 25 изменений в кольце, вытеснение только старейших, уничтожение Redo после нового изменения |

| K | настоящий save после Undo/Redo, Undo после save, возврат к checkpoint, очистка и загрузка другого проекта |

Пагинация проверена на 23 записях: 20+overfetch, затем 3; проверены SQL и
игровой обработчик следующей страницы. Обновление описания и подтверждение удаления
проверены через настоящую диспетчеризацию игровых диалогов с двойником UI.
Поздний insert callback после close/reopen не меняет новую аренду сессии.
Для теста несовместимого формата ограничение CHECK временно снимается **только
в одноразовой тестовой БД**, затем данные и enforcement восстанавливаются.
Production-миграция оставляет CHECK включёнными.

### Нагрузка и ресурсы

Восемь сессий одновременно содержат по 64 элемента, 16 групп и 20 операций.
Выполнены 320 последовательных Undo/Redo свойств: 20 отмен + 20 повторов для
каждой сессии, с проверкой всех checkpoints. Созданий/пересозданий хэндлов при этом
**0**. Прежний тест 3.2 также подтверждает до 20 geometry-обновлений/сек при
1000 входных update/сек/сессию, без записей истории на кадрах.
При вставке/структурном restore нужен запас до 64 временных PlayerTextDraw.
Максимум своих хэндлов: 64 старых + 64 новых + 11 toolbar + 6 grid = **145**.
Чужие UI могут занять остальной пул; отказ в этом случае корректен и протестирован.
Счётчики создания/удаления всех принадлежащих редактору хэндлов сходятся, чужой
хэндл остаётся; неверных native-обращений и переполненных диалогов не зафиксировано.

## Ограничения и ручная приёмка GTA

Полный historical Python-набор не зелёный по прежним несвязанным причинам;
точные совпадающие ID приведены ниже. Новые тесты проходят. Runtime-пул истории
имеет фиксированный резерв 2.77 МиБ до выгрузки AMX, глубина не настраивается
игроком и не переносится между сессиями/серверными процессами.
Сохраняются ограничения 3.2: логические границы текста вместо измерения глифов,
шесть локальных направляющих, якоря X≤640/Y≤448 и размеры прежнего формата.
Невозможная вставка отклоняется целиком. Рестарт MySQL/обрыв сети точно в COMMIT,
runtime-права игрового хостинга и настоящий gmx с игроками не проверены.

Ручные сценарии (ещё **не выполнены**):

1. Через UI создать четыре типа, изменить их свойства/текст/кириллицу, удалить,
   продублировать; Undo/Redo несколько раз, проверить вид и области кликов.
2. Группа TARKENSO_LOGO: перемещение, resize/scale, align/distribute, слои и состав.
   До подтверждения N отменяет локальную операцию без новой записи; после него
   UNDO отменяет весь набор, REDO восстанавливает. Проверить нижние/верхние слои.
3. 20+ действий, очистка с подтверждением/без него, fork после Undo; проверить
   кнопки/подписи, preview hide и отсутствие конфликтов с проектными элементами.
4. Save после Undo, save после Redo, Undo после сохранения, возврат к чистому
   состоянию и загрузка другого проекта. Закрыть/отключиться в незавершённом live
   режиме и во время запроса; повторно открыть, проверить чистую историю.
5. Сохранить личный/общий шаблон из двух групп с кириллицей, перезапустить полный
   мод, найти по категории/страницам, переименовать/изменить описание/удалить.
6. Вставить дважды в другой проект: центр, X/Y и offset; проверить независимость,
   имена групп, размеры/Box/preview/слои, Undo одной вставки и Redo.
7. Обычный разработчик не читает личный чужой и не правит чужой общий шаблон;
   основатель управляет личными, обычный разработчик использует общий.
8. Два и восемь разработчиков с активными UI: заполненный пул, непрерывные
   движения, Undo/Redo, lag/ping, отзыв grant/founder, смерть и gmx. Измерить
   реальный CPU/трафик и визуальное мерцание, не выводить их из synthetic harness.
9. Подключить оба экспорта в тестовый мод по `.txt`, визуально сравнить; затем
   проверить сортировку мусора, меню персонажа, авторизацию и работу администратора.

Браузер, клиентские модификации/лаунчер, PNG/JPG, произвольные модели, внешний
каталог, облачная синхронизация и новые аккаунты не добавлены. Дальнейшее развитие
рекомендуется после этой игровой приёмки и профилирования на целевом хостинге.
