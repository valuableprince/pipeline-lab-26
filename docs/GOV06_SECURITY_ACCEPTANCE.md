# GOV-06 — финальная инженерная проверка государственного займа

**TARKENSO, open.mp/Pawn, MariaDB 10.11 · PR #94 (черновик).**

## Что реализовано

GOV-06 вводит миграцию `024_finance_assurance.sql`. Она:

1. Переключает 21 финансовую SQL-процедуру на `SQL SECURITY DEFINER`,
   чтобы будущему ограниченному пользователю можно было дать право
   `EXECUTE`, **не предоставляя прямого UPDATE финансовых таблиц**.
2. Запрещает `UPDATE` и `DELETE` на 10 финансовых журналах
   через 20 InnoDB-триггеров. Легитимные процедуры работают через
   добавление новых событий. Исправления финансовых результатов
   нельзя выполнять переписыванием истории.
3. Добавляет `CALL gov_finance_assert_integrity()` — диагностическую
   процедуру, которая либо выдаёт `PASS`, либо завершает вызов
   `SQLSTATE 45000`. Она **не меняет баланс**.
4. Управление облигациями привязано к обычной организации №5 —
   Министерству финансов. Ранги проверяются по `faction_members`;
   отдельные финансовые SQL-аккаунты не требуются.

### Инварианты сверки

| Проверка | Обязательное условие |
|---|---|
| Реальная денежная масса казны | `treasury.balance = SUM(treasury_ledger.amount_delta)` |
| Страховой фонд | `F = SUM(bond_fund_ledger.reserve_delta)` |
| Принятое покрытие | `E = SUM(bond_fund_ledger.commitment_delta)` |
| Заблокированные выплаты | `P = SUM(bond_payout_ledger.reserved_delta)` |
| Требования инвесторов | `P = SUM(budget_awarded + insurance_awarded − collected)` |
| Достаточность резерва | `balance >= minimum_reserve + F + P` |
| Допустимость гарантий | `E × 10000 <= F × utilization_basis_points` |
| Выкупленные облигации | `issues.sold_quantity = SUM(orders.quantity)` |
| Права на облигации | `SUM(holdings.quantity) = SUM(orders.quantity)` |
| Реестр получений | `claims.amount_collected = SUM(claim_receipts.amount)` |
| Реальные покупки | Каждая покупка имеет соответствующий положительный `treasury_ledger` |

Отдельно проверяется, что клиент не может получить больше зарезервированных
средств или подменить владельца операции. При ошибке диагностика выдаёт
SQL-исключение; состояние финансов **не скрывается** за ложным OK.

## Реальные автоматические проверки

`tests/gov06_mysql_uat.py` исполняется в отдельной MariaDB **после**
всех миграций 001, 017—023 и финансовых UAT GOV-00—05. Проверяет:

- Запуск сверки на уже созданных займах, дефолтах, гарантиях и выплатах.
- Отказ от `UPDATE` / `DELETE` реальных строк всех журналов.
- Контролируемое нарушение баланса внутри незакоммиченной транзакции:
  `gov_finance_assert_integrity()` должна обнаружить его, затем `ROLLBACK`
  возвращает БД в правильное состояние.
- Ограниченного SQL-аудитора, которому предоставляются только `SELECT`
  на три отчётные таблицы и `EXECUTE` на `gov_finance_assert_integrity`.
  Прямое изменение казны, фиктивное поступление, покупка, назначение
  должности и вызов `treasury_post` должны отклоняться.
- 64 параллельных обращения к отчёту (8 рабочих потоков) без расхождения
  итогов или зависания.
- Структурные и игровые контракты включены в общие Python/Pawn CI.

**Не следует трактовать 64 одновременных чтения как испытание
на 500 игроков или полноценный стресс-тест игрового сервера.**
Нагрузочные испытания всего open.mp остаются отдельной процедурой
приёмки. Ранее существовавшие синтетические тесты AMX продолжают
запускаться в CI.

## Ограничение привилегий и порядок развёртывания

Список SQL-прав в текущем игровом `mysql.ini` необходимо проверить
отдельно. **Недостаточно изменить только `SQL SECURITY DEFINER`**:
если игровой пользователь сохраняет `ALL PRIVILEGES` или
`UPDATE` на финансах, он всё ещё может напрямую изменять балансы
и обойти бизнес-процедуры. Аналогично прямой `UPDATE accounts.balance`
существует в основной подсистеме сохранения персонажей.

Это **критический эксплуатационный риск до ограничения прав основного
игрового SQL-пользователя**. Текущий PR не выдаёт гарантию защищённости
от компрометации учётных данных общего `mysql.ini` и потому не должен
устанавливаться как публичная платёжная система без дополнительного
ревью всех DB ACL. Реализованные аудиторские триггеры защищают
исторические записи, но не заменяют запрета прямого UPDATE таблиц
казны и счетов.

Кадровые действия выполняются через уже существующие `/setleader`,
`/finvite`, `/faccept` и `/frank`; новой SQL-роли или
подключения `mysql-govadmin.ini` в системе нет.

## Приёмка перед слиянием

Условия ручной приёмки (владелец проекта принимает **один раз после
GOV-00—06**, не по отдельным промежуточным этапам):

1. На тестовой БД миграции 017—024 устанавливаются ровно один раз,
   от ранее созданных пользователей ничего не теряется.
2. В обычном клиенте open.mp команда `/bonds` видит открытые выпуски,
   покупает **ровно одну** бумагу, отображает её в портфеле.
3. Специалист: создание → утверждение руководством; зам/министр:
   создание → автоматическое утверждение без второй подписи; затем открытие;
   отмена только без владельцев.
4. Сквозной код `GOV-000001`, `GOV-000002`, ... без года и повторов.
5. Два параллельных покупателя последней бумаги: успех только у одного.
6. Покупка, списание, страховка и погашение — точные суммы.
7. Погашение при выключенном игроке: офлайн-выплаты сохраняются.
8. Дефолт и повторные поступления: сохраняются все остаточные требования.
9. Остановка сервера во время операции и повтор с тем же `event_key`:
   максимум одна успешная финансовая проводка.
10. У пользователя без роли нет команд выпуска и отмены; после
    отзыва должности старые диалоги и токены не помогают.
11. SQL-логин ограничен насколько позволяет существующая система;
    подтверждён реальный перечень его прав и отсутствие внешнего доступа.
12. Выполнены реальные игровые нагрузочные испытания при плановой
    массовой выплате и входе десятков игроков; результаты зафиксированы.

Готовность для **CI и стендовых технических испытаний** не равна
