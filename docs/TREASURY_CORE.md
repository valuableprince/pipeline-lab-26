# TREASURY-01 — казна государства (TARKENSO)

## Назначение и границы этапа

Казна — единый глобальный бюджет государства (`code='state'`). Числового `treasury_id` нет: фиксированный первичный ключ `code` и SQL `CHECK (code='state')` разрешают ровно одну запись с предустановленным кодом. В `treasury_ledger` также нет идентификатора казны: каждая запись журнала относится к этому единственному бюджету. Она **не является кошельком персонажа**: `accounts.balance`, `Economy_Credit`, `Economy_Debit`, PayDay, зарплаты и существующие работы на этом этапе не меняются. Деньги в казну пока автоматически не поступают и не списываются. Никаких новых пользовательских или административных команд пока нет.

Источник истины — MySQL/MariaDB. Pawn хранит только снимок для чтения. Любая будущая интеграция должна обращаться к серверному API, а не изменять значение переменной `gTreasuryBalance` или SQL-таблицы напрямую.

## Структура БД (миграция 017)

| Таблица | Назначение |
|---|---|
| `treasury_accounts` | Единственная строка с фиксированным кодом `state`, балансом, статусом, разрешениями поступлений/расходов, минимальным резервом, лимитом операции, налоговой ставкой, версиями состояния/настроек и датами |
| `treasury_ledger` | Неизменяемая история проводок единственной казны: глобально уникальный `event_key`, знак суммы, баланс после операции, источник, автор (необязателен), примечание и время |

При применении миграции создаётся **одна пустая государственная казна** в `treasury_accounts` (баланс 0), разрешены поступления и расходы, минимум остатка 0, максимальная разовая операция 1 000 000 000, ставка налога 0. Это только настройки **для будущих механик**, без автоматического их исполнения.

Баланс ограничен 2 000 000 000, сумма одной проводки — 1 000 000 000, потому что в данном Pawn-рантайме суммы читаются в знаковый 32-разрядный `cell`. При расширении экономики сверх этого предела нужно отдельно спроектировать 64-разрядное представление. В SQL хранятся `BIGINT`, чтобы не мешать дальнейшей миграции.

Ставка `income_tax_basis_points`: 100 = 1 %, 1000 = 10 %, 10000 = 100 %. **Текущий этап налог не рассчитывает и не удерживает.**

## Порядок внедрения

1. Сделать резервную копию БД. На тестовой базе с применёнными миграциями 001–016 выполнить **один раз** `db/migrations/017_treasury_core.sql` под отдельным migration-пользователем с DDL и CREATE ROUTINE.
2. Runtime-пользователю MySQL выдать минимальные права: `SELECT` и **колоночный** `UPDATE (balance, row_version)` на `treasury_accounts`, `SELECT, INSERT` на `treasury_ledger`, `EXECUTE` на `treasury_post`. Настройки (`income_enabled`, `expense_enabled`, `minimum_reserve`, `max_transaction`, `income_tax_basis_points`) runtime-пользователь изменять не должен: для этого нужна отдельная администраторская учётная запись. Поскольку процедура использует `SQL SECURITY INVOKER`, DML-права на баланс и журнал пока требуются и вызывающему пользователю. Не выполнять прямые UPDATE/INSERT из Pawn: баланс и журнал должны изменяться вместе через процедуру.
3. Сборка с `TARKENSO_DB_PRIMARY` использует существующее подключение `gDBPrimary` и `mysql.ini`. Модуль `gamemodes/includes/treasury.inc` подключается после `db_primary.inc`; при запуске выполняет `Treasury_Init()`, при остановке — `Treasury_Shutdown()`.
4. При отсутствии миграции 017, недоступности БД или файловом режиме сервер продолжает работать, но казна **неактивна**: все вызовы её денежного API возвращают false. Отсутствие миграции не должно ломать старые игровые системы. После установки миграции требуется `Treasury_Reload()` или перезапуск сервера.

## API Pawn

```pawn
Treasury_IsReady(); // bool: доступна ли казна
Treasury_GetBalance(); // баланс, -1 если казна недоступна
Treasury_Reload(); // перечитать актуальные состояние и настройки из БД
Treasury_Credit(250, "cargo-trip-502", "ship_cargo", "completed_delivery");
Treasury_Debit(100, "purchase-105", "public_spending", "equipment");
```

Необязательный последний аргумент для `Treasury_Credit`/`Treasury_Debit` — `actorAccountId` (положительный идентификатор `accounts.account_id` либо 0 для системного события). Не передавать `playerid` вместо ID аккаунта. `eventKey` и `source` — только стабильные ASCII-идентификаторы (буквы, цифры, `_`, `-`, `:`, `.`, `/`), максимум 64 и 32 символа соответственно. Ключ события обязан быть уникальным **для смыслового события**, и оставаться тем же при повторной попытке. `note` — описание до 120 символов/байтов в Pawn; не включать туда секреты.

`Treasury_Post` вызывает **один** `CALL treasury_post(...)` синхронно. SQL-процедура в InnoDB выполняет `START TRANSACTION`, блокирует общую строку баланса **и настроек** в `treasury_accounts` через `FOR UPDATE`, проверяет настройки, допустимый остаток и событие, меняет баланс и создаёт запись в `treasury_ledger`, затем `COMMIT`. При SQL-ошибке выполняет `ROLLBACK`.

Повтор с тем же `event_key`, суммой, источником, автором и примечанием считается идемпотентным: баланс не меняется второй раз, а процедура возвращает текущий баланс с `replayed=1`. Повтор того же ключа с другим содержимым отвергается. Результат `true` означает, что проведение или подтверждённый повтор завершились успешно; повтор отдельно отмечается в серверном логе.

**Важно:** синхронный SQL-вызов блокирует игровой поток на время обращения к БД — это ограниченный инфраструктурный API для редких операций на первом этапе, **не использовать в таймерах на каждого игрока**. Для массовых выплат необходим асинхронный обработчик очереди с уникальными событиями и согласованным изменением игрока и казны. Сам по себе успешный `Treasury_Credit` не гарантирует атомарности с `Economy_Credit`; интегрировать двусторонние переводы без общей транзакционной схемы нельзя.

## Проверка на тестовом сервере

После миграции проверить, что:

- `SELECT * FROM treasury_accounts WHERE code='state';` возвращает баланс 0 и начальные настройки из **одной строки**. Попытка создать казну с иным `code` отвергается ограничением CHECK.
- `CALL treasury_post('uat-credit-001',100,'uat',NULL,'initial_test');` увеличивает баланс до 100 и создаёт ровно одну строку журнала.
- Повтор **той же** команды возвращает `replayed=1`, баланс 100, в журнале всё ещё одна строка.
- `CALL treasury_post('uat-credit-001',200,'uat',NULL,'initial_test');` отвергается из-за конфликта ключа.
- Списание `CALL treasury_post('uat-debit-001',-25,'uat',NULL,'initial_test');` приводит к балансу 75. Списание сверх остатка отвергается без изменения баланса или журнала.
- Изменение `minimum_reserve`, `expense_enabled` или `max_transaction` меняет разрешённость **следующих** проводок; обновление выполняется вручную только на staging, затем проверить `Treasury_Reload()`.
- Перезапуск сервера восстанавливает баланс из БД, а при отсутствии 017 отключается только казна.

Это ручные SQL/серверные сценарии; статические Python-тесты не заменяют реальный MySQL/MariaDB и компиляцию Pawn. Ввод тестовых проводок на production запрещён без специально предусмотренной процедуры отката (журнал не удалять и не править).
