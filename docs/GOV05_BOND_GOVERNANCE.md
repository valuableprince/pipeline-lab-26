# GOV-05 — Государственное управление выпусками облигаций TARKENSO

**Ветка:** `feat/gov00-atomic-transfers`. **Накопительный PR #94**, не переносить в `main` до финальной приёмки.

## Назначение

Два раздельных интерфейса: **`/bonds`** для любого инвестора и **`/bondgov`**
для уполномоченных работников государственного казначейства.

Создание облигаций не требует ввода кода выпуска. Он формируется
**сервером MySQL внутри одной InnoDB-транзакции**, автоматически:
`GOV-2026-0001`, `GOV-2026-0002`, `GOV-2027-0001` и т. д.
Номер уникален в календарном году UTC, начинается с 0001, не
переиспользуется после отмены выпуска, не меняется после создания.
Предусмотрено 9999 выпусков за один год. При старте миграция учитывает
выпуски, коды которых ранее были присвоены вручную в таком же формате.

## Государственные должности

В текущем моде нет отдельной государственной финансовой фракции.
Система GOV-05 не подменяет ни шерифов, ни медслужбу, ни радио:
вместо этого назначаются самостоятельные должности
`government_bond_officials`, привязанные к настоящему SQL-аккаунту.

| Роль | Создать проект | Утвердить | Открыть | Отменить непроданный |
|---|---|---|---|---|
| TREASURER (казначей) | Да | Нет | Да | Нет |
| CONTROLLER (контролёр) | Нет | Да | Нет | Да |
| DIRECTOR (руководитель) | Да | Да¹ | Да | Да |

¹ **Свой собственный** выпуск директор утвердить не вправе: всегда
требуются два **разных** SQL account ID. Страховое обеспечение
блокируется в одной SQL-транзакции GOV-02 с утверждением. Отмена
проданного выпуска запрещена, в том числе при ошибочном счётчике
продаж, если есть записи держателей.

Назначение и отзыв должностей протоколируются в
`government_bond_role_audit` с уникальным event key.
Назначать может только **основатель TARKENSO в режиме `/aduty`**,
через серверную команду:

`/bondgovrole [ID онлайн-игрока] [роль: 1/2/3] [доступ: 0/1]`

Например, `/bondgovrole 12 1 1` назначает казначеем ID 12,
а `/bondgovrole 12 1 0` отзывает полномочия.
Цель должна быть авторизована и иметь SQL-primary аккаунт.

Критически важное ограничение GOV-05: проверка основателя
в текущем проекте находится **в Pawn**, потому что разрешения
администраторов хранятся в файловом реестре. До выполнения GOV-06
право SQL `CALL gov_bond_role_set` должно быть закрыто извне
сервисными ограничениями доступа к БД. План GOV-06 включает
минимально необходимые привилегии DB-аккаунта и процедуру
безопасной регистрации полномочий. **Не считать текущую схему
защищённой от компрометации прямого MySQL-доступа.**

## Как работает /bondgov

### 1. Главное меню

Стандартный цветной SA-MP/open.mp `DIALOG_STYLE_LIST`:

1. Новый государственный заём.
2. Реестр выпусков и решения.
3. Финансовая отчётность.
4. Назначение финансовых должностей (инструкция основателю).

Сведения о роли и выпусках загружаются из MySQL, не из
клиентского списка. Для списков выпусков используется
`DIALOG_STYLE_TABLIST_HEADERS`, 10 выпусков на страницу, с
защищёнными индексами строк и корректными пустыми состояниями.

### 2. Создание выпуска

После выбора типа (общий / целевой / антикризисный) запускается
последовательный мастер из **семи шагов**:

1. Название займа (3—128 символов).
2. Назначение займа (3—192 символа в данном игровом мастере).
3. Номинал одной облигации (1—1 млрд долларов).
4. Количество облигаций (1—1 000 000).
5. Доходность за весь срок (базисные пункты: 150 = 1,50%).
6. Срок первичного размещения (1—30 суток UTC).
7. Срок после окончания продажи до погашения (1—365 суток).

Произведение номинала на количество не должно превышать
$1 млрд — это независимо проверяет SQL. После завершения мастер
показывает отдельный экран подтверждения, перечисляющий все
параметры. Код автоматически назначает MySQL.

Выпуск регистрируется как `DRAFT`; ни одной облигации ещё
не продано, бюджет не пополнен. Покупка из `/bonds` ещё невозможна.

### 3. Утверждение и размещение

Управление выпуском осуществляется через карточку реестра.
Утверждение доступно контролёру или руководителю, **но не
создателю выпуска**. MySQL в рамках подтверждения резервирует
страховую ёмкость F/E и замораживает условия эмиссии.
Открыть продажу сможет казначей/руководитель в установленные
выпуском сроки. После OPENING/OFFERING облигации появляются
в гражданском `/bonds`, где можно купить одну бумагу за раз
и увидеть её в портфеле.

Отменять можно только выпуски без проданных облигаций и
без прав держателей. Освобождение гарантий атомарно.

### 4. Финансовая отчётность

Данные поступают непосредственно из SQL:

- Баланс единой казны.
- Страховой фонд F и принятое обеспечение E.
- Защищённый расчётный резерв ожидающих выплат P.
- Состояние финансов (NORMAL, STRESSED, DEFAULT, RECOVERY).
- Общее количество выпусков и открытых размещений.
- Общее число проданных облигаций и размер необеспеченного долга.

**Четвёртый пункт** обычного `/bonds` содержит
**публичную отчётность** с этими же показателями; доступен
обычным игрокам, чтобы инвесторы могли оценивать риски.
Публичная функция только читает SQL и не предоставляет
разрешений на выпуск или списание средств.

## Технические файлы

- `db/migrations/023_bond_governance.sql` — государственные должности,
  аудит, годовой генератор кодов и новые SQL-процедуры.
- `gamemodes/includes/bond_governance_ui.inc` — управление через Dialog
  ID **6800—6807**, внутреннее состояние мастера, чтение прав,
  проверка авторизации, асинхронные SQL callback и отчёт.
- `gamemodes/includes/commands.inc` — `/bondgov`, `/bondgovrole`.
- `gamemodes/includes/bonds_ui.inc` — публичная отчётность инвесторов.
- `tests/gov05_mysql_uat.py` — интеграция на реальной MariaDB:
  номера 0001—0009, 6 конкурентных выпусков, разделение подписей,
  отзыв роли, резервирование/освобождение F/E.
- `tests/test_bond_governance.py` — контрактные тесты.

Все административные действия имеют уникальные серверные event keys;
подтверждение диалога нельзя повторно использовать для нового списания
или выпуска. При бизнес-отказе SQL пользователь получает сообщение,
а остальные игроки продолжают работать.

## Автоматические страховые отчисления с налогов

Ставка **5%** уже хранится в GOV-01 как
`treasury_accounts.bond_fund_tax_allocation_bps = 500`.
GOV-05 вводит `government_bond_tax_earmarks` и
`gov_bond_tax_earmark(fund_event_key,tax_event_key)`.

После фактической записи **положительного** поступления в
`treasury_ledger` со строго указанным `source='tax'`, фоновый
обработчик казначейства находит нераспределённые налоговые события и
резервирует соответствующую долю существующих денег в F.
Если нет свободных средств — транзакция отклоняется и будет
проверена повторно. Отчисление не меняет общую сумму казны.
Повторный вызов безопасен; для каждого налогового `ledger_id`
разрешено только одно событие вида `fund:tax:<ledger_id>`.

Доля округляется вниз до целой игровой денежной единицы;
для небольшого налога с результатом 0 фиксируется обработанное
поступление без нулевой записи в `bond_fund_ledger`.
Сверка `government_bond_tax_earmarks` ↔ `bond_fund_ledger`
и ограничение `F + P ≤ treasury_balance` входят в тесты.

В текущем моде GOV-05 не создаёт отдельный механизм сбора налогов:
обработчик работает на **реально поступивших** налогах.
Выпуск облигаций и налогообложение не генерируют деньги автоматически.
