## Инструменты и управление

`/tdstudio` → «Редактировать интерфейс» → **«Геометрия: размер / масштаб / сетка»**.
Этот же раздел добавлен в свойства активного элемента и меню группы.
Новых команд нет. Выделение, активный элемент и группы используются из этапа 3.1.

| Действие | Поведение |
| --- | --- |
| Изменить размер области | клавиатура меняет W/H только активного элемента, даже если выделена группа |
| Изменить размер букв | только текст, меняет LetterX/LetterY, оставляя W/H области |
| Масштабировать выделение / группу | меняет позиции и применимые размеры всех выбранных участников |
| Точные X Y W H LetterX LetterY | шесть чисел для активного элемента; для остальных типов LetterSize игнорируется |
| Точная позиция опоры | один общий вектор для выделения/группы; для одиночного элемента это якорь TextDraw |
| Точный масштаб X Y | множители, например `1.5 1.5`; при сохранении пропорций X используется для обеих осей |
| Выравнивание | шесть направлений, относительно активного элемента или общего прямоугольника выделения |
| Распределить | по горизонтали/вертикали, минимум три элемента, равные свободные промежутки |
| Позиция относительно экрана | центр, слева/справа/сверху/снизу, центр сверху/снизу; настраиваемый отступ |
| Сетка и Snap | шаг 2/5/10/20; математическая привязка и визуализация включаются независимо |
| Параметры и границы | X/Y, область, LetterSize/align текста, границы/размер набора, имя/ID группы, опора и шаги |

Для выравнивания группы **целиком** по другому элементу: сначала выбрать группу
через раздел «Группы», затем обычным выбором сделать внешний элемент активным.
«Геометрия → Выровнять ранее выбранную группу по активному» использует последний
`tsGroupFocus`. Группа получает единый вектор; ориентир остаётся на месте.
Отсутствующая группа или ориентир внутри неё отклоняются. Обычное «Выровнять
выбранные элементы» располагает участников по отдельности, в том числе членов группы.
Экранные команды всегда перемещают всё текущее выделение как единый объект.

### Клавиатурная операция

Вход требует персонажа пешком, отсутствия чужой блокировки/диалога и завершённых
DB-заданий. Редактор освобождает курсор, замораживает персонажа своей арендой и
ждёт нейтрального пакета. Стандартный API передаёт **действия GTA, а не физические
коды клавиш**; названия привычных клавиш ниже относятся к стандартной раскладке.

| Действие open.mp | Обычно | Resize/Scale |
| --- | --- | --- |
| `leftright`, `KEY_LEFT/KEY_RIGHT` | A/D, стрелки | уменьшить/увеличить W |
| `updown`, `KEY_UP/KEY_DOWN` | W/S, стрелки | уменьшить/увеличить H |
| `KEY_CROUCH` | C | ось 0: обе → 1: только W → 2: только H |
| `KEY_SPRINT` | Space | следующий шаг 0.1 / 0.5 / 1 / 5 / 10 |
| `KEY_SECONDARY_ATTACK` или `KEY_YES` | Enter / Y | подтвердить |
| `KEY_NO` | N | отменить; при одновременном подтверждении отмена имеет приоритет |
| `/tdstudio` | команда | отменить и вернуться к меню |

В режиме только W/H второе направление также управляет выбранной осью; при
диагональном вводе предпочтение у её собственного направления. При сохранении
пропорций и одновременном вводе двух осей ведущей является W, иначе — H.
Шаг resize независим от прежнего шага перемещения. Включение пропорций и выбор
опоры (центр / левый верх) выполняются до входа в операцию. Обычный move сохранён.
Esc без TextDraw-курсора серверу не сообщается; использовать N или команду.

## Архитектура и геометрия

`tdstudio_geometry.inc` — вычисления, ограничивающие прямоугольники, план и общий
commit. `tdstudio_geometry_ui.inc` — игровые диалоги. `tdstudio_grid.inc` владеет
только вспомогательными хэндлами. Ввод, жизненный цикл, слои и группы остаются
в существующих модулях. Второй модели координат и отдельной системы групп нет.

Сериализуемая `E_TDS_ELEMENT` **не менялась**: рабочими остаются `tdX`, `tdY`,
`tdW`, `tdH`, `tdLetterX`, `tdLetterY`. `E_TDS_GEOMETRY` задаёт индексы временного
снимка этих шести полей. `gTDSOrigin` заменяет прежний X/Y-снимок движения и хранит
исходную геометрию участников. Их исходные ID проверяются через `gTDSMoving`.
Статический `gTDSGeoPlan[64][6]` — короткоживущий план синхронной операции,
без callback/асинхронного срока жизни. Никакие его значения не сериализуются.

### Разные типы TextDraw

| Тип | Область для геометрии | Обновление и масштабирование |
| --- | --- | --- |
| Текст, шрифты 0..3 | left/center/right учитывают якорь: `x`, `x−w/2`, `x−w`; top=`y` | W/H — логическая область; LetterSize — отдельный размер глифов |
| Прямоугольник / TXD | левый верх X/Y, ширина W, высота H | font 4, native TextSize получает W/H |
| Preview модели | левый верх X/Y, ширина W, высота H | font 5, native TextSize получает W/H; Zoom/повороты не меняются |

Прежний адаптер TextSize сохранён: левый текст получает endpoint `x+w`, правый
`x−w`, центрированный — переставленные H/W. Масштаб группы умножает W/H всех
типов и LetterX/Y **только текста**. Отдельный area-resize текста не меняет буквы;
glyph-resize не меняет область. Контур, тень, font, alignment, цвета, Zoom и
прочие свойства сохраняются. `tdProportional` шрифта и «сохранять пропорции»
геометрии — разные настройки.

Границы текста — прямоугольник **области размещения модели**, а не измеренный
контур видимых букв. Метрики шрифта, переносы, обводка и специфические отступы
Box не измеряются. Пиксельно точное выравнивание по чернилам глифов не обещается.
Проверены [TextSize](https://open.mp/docs/scripting/functions/PlayerTextDrawTextSize),
[Alignment](https://open.mp/docs/scripting/functions/PlayerTextDrawAlignment),
[LetterSize](https://open.mp/docs/scripting/functions/PlayerTextDrawLetterSize),
[GetPlayerKeys](https://open.mp/docs/scripting/functions/GetPlayerKeys) и
[виртуальные координаты](https://open.mp/docs/scripting/functions/CreatePlayerTextDraw)
вместе с заголовками установленного SDK 1.5.8.3079.

### Масштаб и атомарность

При старте фиксируются шесть исходных полей, общий прямоугольник, размеры и опора P.
Для каждой новой пары размеров получаются `sx = newW/originalW`, `sy = newH/originalH`.
Позиции вычисляются как `P + (originalPosition−P)*scale`, размеры — как
`originalSize*scale`. Расчёт идёт от первоначального снимка, а не предыдущего кадра.
При пропорциях `newH = originalH*(newW/originalW)` либо симметрично по H.
Деление допускается только после проверки положительного исходного размера.

До первой записи проверяются **все** кандидаты, индексы, ID и native-хэндлы.
Невалидный участник отклоняет весь план. Затем записывается весь набор и
обновляются только затронутые элементы. При отмене сначала восстанавливаются
все поля в модели, затем их представление. Dirty меняется только после
подтверждения фактического изменения; прежний dirty отмена не сбрасывает.
ID, порядок слоёв, состав группы и свойства вне геометрии не меняются.

Рендер использует существующие хэндлы: hide → SetPos/LetterSize/TextSize → show.
Для одного переноса LetterSize не пересылается. Эти natives не выделяют ресурсы
и не вызывают Pawn callbacks между предварительной проверкой и обновлением.
Масштабирование не требует пересоздания набора и не меняет native-порядок слоёв.
При пропавшем хэндле клавиатурная операция безопасно закрывается через прежний
жизненный цикл. Для смены слоёв остаётся транзакционное пересоздание этапа 3.1.

### Выравнивание, распределение и экран

Шесть направлений используют края/центры логических прямоугольников, а не просто
разницу X/Y. При ориентире на активный элемент он не перемещается. При ориентире
на выделение фиксируется общий прямоугольник до операции. Для группы/экранных
команд применяется один вектор всем участникам. Точная позиция задаёт выбранную
опору группы/набора, для одиночного элемента — его собственный якорь.

Распределение стабильно сортирует по left/top, затем по постоянному ID.
Крайние элементы остаются; промежуток равен
`(lastEnd−firstStart−sum(extents))/(N−1)`. Меняются только позиции внутренних
элементов. Отрицательный промежуток отклоняется с сообщением, не включая скрытый
режим пересечений и не изменяя размеры.

Экранные команды используют **640×480**, центр **320/240**, независимо от
разрешения клиента. Отступ — 0..224 виртуальных единиц. Якорные ограничения
существующего формата 2 сохраняются: X **0..640**, Y **0..448**; размеры W
**0.1..640**, H **0.1..448**, LetterX **0.01..5**, LetterY **0.01..10**.
Если размещение у нижнего края потребовало бы якоря Y>448, вся операция отклоняется.
Например, область высотой 10 при нулевом отступе требует Y470; при отступе 40
получает допустимый Y430. Верх/центр и нижнее размещение достаточной высоты работают.

Расширение Y/H до 480 затронуло бы CHECK/проверки процедур схемы 012/015,
валидатор, move и совместимость старого runtime-писателя. На этом этапе сохранён
действующий контракт хранения, а не введена новая схема ради нижней полосы.
Это **ограничение редактора/формата, а не запрет API open.mp**. Невозможные команды
не маскируются под успешные и не смещают только часть группы.

### Grid и Snap

Полная сетка с шагом 2 потребовала бы более 500 линий при лимите 256 PlayerTextDraw
на игрока. Реализованы **шесть локальных направляющих**: три вертикальные и три
горизонтальные через ближайшие узлы около опоры. Это облегчённая визуализация,
не полный графический фон. Линии non-selectable, font 4, alpha 0x30; клетки/хэндлы
кэшируются. Без смены клетки обновления линий не посылаются. Хэндлы создаются
лениво, частичный отказ освобождает только временные ресурсы; Snap доступен и без них.
В меню/preview сетка скрыта, при выключении/закрытии освобождается. Проектные
хэндлы и слои не переставляются. Максимум с 64 элементами и их временной копией
при смене слоёв: 64+64+9 служебных+6 сетки = **143** принадлежащих редактору хэндла.

Snap включается независимо и сам координаты не меняет. Одиночное движение
привязывает якорь, группа/набор — общую выбранную опору. Пересечение допустимых
дельт всех участников определяет ближайший разрешённый узел. Один вектор
сохраняет взаимные смещения. При удержании накапливается **неснапнутое намерение
от исходного снимка**, а не округлённая координата предыдущего кадра. Поэтому
шаг 0.1/1 продолжает перемещать объект при сетке 10. Точные координаты и старый
диалог позиции используют ту же привязку; у верхнего предела выбирается допустимый
узел (Y448 → Y440 при шаге 10). Выравнивание, распределение и масштабирование
не округляются поэлементно: это разрушило бы их геометрические условия.

## Хранение, безопасность и производительность

**Миграций нет. 012 и 015 не менялись. Формат остаётся 2.** Существующие кодек,
параметризованные асинхронные процедуры и CAS-ревизии сохраняют изменённые шесть
полей вместе с ID/слоями/группами. SQL на кадрах/клавишах отсутствует. Save As,
старые v1/v2 проекты и экспорт пользуются прежней инфраструктурой/подключением.
Сетка, Snap, отступ, опора, ось, шаг и режим пропорций — настройки текущей аренды
сессии; между проектами в ней сохраняются, после закрытия редактора/нового процесса
сбрасываются. Выделение и снимки операции не сериализуются.

Входные точки проверяют подтверждённую сессию, владельца/права, проект, busy и
конфликтующий клавиатурный режим. Чужие проекты/аренды недоступны. Проверяются
лимиты 64 элементов, 16 групп, 8 сессий; прежний command/click throttle сохранён.
Диалоги **7126..7132** выделены в общем диапазоне и проверены на конфликты.
Числовой парсер прежний: строгие десятичные значения, до трёх знаков после точки;
NaN/inf/экспоненты/хвосты/слишком длинные строки отклоняются. Прямые Float API
также отбрасывают NaN/inf, отрицательные/нулевые недопустимые размеры и переполнения.

Обновления идут через существующий `OnPlayerUpdate` с интервалом **50 мс (20 Гц)**,
не через новые таймеры. Обычный пакет даёт один шаг; максимум два кванта после
задержки, после 250 мс требуется нейтральный ввод. Конфликтующие save/load/export,
выбор/слои/группы заблокированы на время операции; геометрия — на время DB-задания.
Disconnect, отзыв прав, смена состояния, закрытие и shutdown очищают все временные
поля и освобождают только принадлежащую этой сессии блокировку управления.

## Экспорт

Генератор не менялся: `TDS_Order` → обычные TextDraw в правильном порядке,
с новыми координатами, TextSize и LetterSize. Group runtime-сущности не создаются;
сетку сериализовать/экспортировать нечему. CP1251 и существующая обработка русского
текста, кавычек, слешей и процентов сохранены.

Фактические примеры генератора, перекодированные в UTF-8 для репозитория:
[PlayerTextDraw](examples/tdstudio_geometry_player_example.inc) и
[Global TextDraw](examples/tdstudio_geometry_global_example.inc).
Их CP1251-байты совпадают с протестированным runtime-выводом. Содержат пять
элементов в порядке **5/1/2/3/4**: позиции **20/20, 260/170, 380/170, 260/190,
380.125/190.25**. Центрированный текст имеет LetterSize **0.5/0.5**, TextSize
**10/80**; спрайт **81/16**, preview **60.125/20.375**.

Runtime-путь остаётся `scriptfiles/tdstudio_exports`, пользователь пути не задаёт.
Для подключения перенести выбранный `.inc` к include-файлам мода, включить после
`<open.mp>` и выполнить Create/Show/Hide/Destroy по соседнему `.txt`. Для Player
вызовы создания/освобождения принимают playerid; для Global создание/освобождение
общие. Репозиторные UTF-8-примеры перед компиляцией стадировать в CP1251 так же,
как основной мод. В тестовом контексте использованы **все** lifecycle и Hit функции.

### Воспроизведение

Использовать SDK 1.5.8.3079 и команды [этапа 2](TEXTDRAW_STUDIO_STAGE2_VALIDATION.md).
Запускатель MySQL **сбрасывает только явно указанную отдельную БД `tds_test*`**;
рабочую серверную конфигурацию ему не передавать. Применяются существующие
миграции 001..012 и 015, новая схема для геометрии не нужна.

```sh
python3 tools/test_tdstudio.py --server /path/to/open.mp/Server --output build/stage32-behavior
python3 tools/test_tdstudio_stage2.py \
  --server /path/to/open.mp/Server \
  --plugin /path/to/mysql-R41-4-Debian \
  --mysql-config /path/to/test-only-mysql.ini \
  --mysql-client /path/to/mysql \
  --output build/stage32-final-integration
python3 -m unittest discover -s tests -p 'test_tdstudio.py' -v
```

Первый запуск включает `tdstudio_geometry_tests.inc` в прежний harness. Второй
сохраняет прежние проверки и добавляет `tdstudio_stage32.pwn` + новый процесс.
На среде без прямого x86 использован `--prefix` с qemu-i386 и `TMPDIR=/dev/shm`.
Основной мод собран тем же UTF-8 → CP1251 staging и `TARKENSO_DB_PRIMARY`, что CI.

`build/stage32-final-integration/{tdstudio-mysql-run,tdstudio-restart-run}.log`,
подкаталоги `stage31` и `stage32` с отдельными run/restart/compile журналами.
