# GOV-01 — Страховой фонд государственных облигаций

**TARKENSO / open.mp / Pawn / MySQL · Стадия разработки, не для production-активации.**

## Модель и утверждённые параметры

В TARKENSO есть ровно одна государственная казна `treasury_accounts(code='state')`.
Фонд гарантирования облигаций — **защищённая доля существующих денег** внутри
этой же казны, не вторая касса и не генератор денег.

| Параметр | Колонка | Старт |
|---|---|---:|
| Денежный резерв фонда | `bond_fund_reserved` | 0 |
| Принятая максимальная страховая ответственность | `bond_fund_committed` | 0 |
| Разрешение новых гарантий | `bond_fund_enabled` | 0 (выключено) |
| Покрытие невыплаченного номинала | `bond_fund_coverage_bps` | 2000 (20%) |
| Взнос из размещения облигаций | `bond_fund_premium_bps` | 200 (2%) |
| Максимальная загрузка фонда | `bond_fund_utilization_bps` | 8000 (80%) |
| Отчисление из налогов | `bond_fund_tax_allocation_bps` | 500 (5%) |
| Льготный период при дефолте | `bond_fund_grace_seconds` | 86400 с |

`balance` обозначим B, `minimum_reserve` — M, резерв фонда — F, обязательства — E.

**Инварианты:** `0 <= F <= B`, `E * 10000 <= F * utilization_bps`.
Для обычных расходов `available = max(0, B - M - F)`. Поскольку M и F имеют
разные правовые назначения, **они складываются**, а не считаются через `max()`.

При F=130000 и E=100000 при загрузке 80% новая гарантия запрещена,
пока `E+new_exposure <= 104000`. Даже полный совместный дефолт не
может потребовать больше предоплаченного лимита. 20% фонда остаются запасом.

### Что реализовано в GOV-01

- Миграция **019** расширяет *существующую единственную строку* казны
  колонками фонда и проверками на уровне MySQL.
- `bond_fund_ledger`: append-only журнал капитализации и резерва гарантий,
  с уникальным `event_key` и ссылкой на актор-аккаунт, если он есть.
- `bond_fund_guarantees`: обеспечение для будущего конкретного выпуска по
  уникальному `issue_code` (выпуски сами будут на GOV-02).
- `bond_fund_capitalize(event_key, amount, actor_account_id)`: только
  перенос денег в защищённую категорию **без изменения B**. Транзакция
  блокирует строку казны, проверяет M и F, атомарно ведёт фондовый журнал;
  повтор события проходит без повторного резервирования.
- `bond_fund_commit(event_key, issue_code, exposure, actor_account_id)`:
  блокирует ёмкость под будущий выпуск с уникальным кодом. Нельзя выдавать
  обещания сверх 80% F, нельзя дважды заложить ту же ёмкость.
- Миграция 019 **заменяет** обе исходные SQL-процедуры
  `treasury_post` и `gov_transfer_post`, добавляя к списаниям
  проверку защищённых средств. Старые миграции 017/018 не меняются.
- `bond_fund.inc`: запрос/снимок фонда, асинхронные внутренние API,
  ограничение очереди одной операцией, защита от сомнительных ACK.
- MariaDB UAT и Python структурные проверки в GitHub Actions.

### Что НА ЭТОМ ЭТАПЕ сознательно отключено

- Ни одна команда игрока/администратора не выдаёт гарантии или не переводит
  деньги фонда. Нет автоматического расходования или пополнения.
- Не выпущено ни одной облигации. `bond_fund_enabled=0` по умолчанию.
- **Нет выплаты страховки**: переводы из F в кошельки будут добавлены
  только вместе с подтверждёнными требованиями и реестром держателей на GOV-03.
- Нет деблокирования страховой ёмкости или вывода средств из F: это
  безопасно только после подтверждения отсутствия проданных/непогашенных
  облигаций, которое появится на GOV-02/03.
- Значения ставки 2% и отчисления налогов 5% пока лишь настройки.
  Автоматическое отчисление реализуется вместе с реальными транзакциями
  размещения и налоговыми поступлениями. Нельзя начислять их без денежного
  источника.
- Новая процедура принимает actorAccountId для аудита, но ещё нет
  связанного RP-воркфлоу полномочий (финансовый руководитель/правительство).
  Не выдавайте `EXECUTE` произвольным игрокам или внешнему API.

## Как работает капитализация (пример)

B=200000, M=10000, F=0, E=0.

`CALL bond_fund_capitalize('fund:capital:0001',100000,NULL);`

После: B=200000, M=10000, F=100000, E=0.
Общий бюджет в наличии остался 200000, но на обычные нужды доступно
только `B-M-F=90000`. Повтор *того же* `event_key` ничего не меняет.

При `bond_fund_enabled=1` процедура
`CALL bond_fund_commit('fund:issue:0001','GOV-0001',80000,NULL);`
резервирует максимум 80000 выплат. Второй такой же запрос идемпотентен.
Попытка увеличить E выше 80000 отклоняется. Это резерв **ёмкости**,
не дополнительный расход из казны.

## Порядок внедрения

**НЕ применять на рабочем сервере до полной пользовательской приёмки
всей финансовой системы.** Пользователь принимает GOV-00—GOV-06 только целиком.

1. На изолированной staging-БД сделать backup, убедиться, что 017 и 018
   уже применены. Если нет — применить их в строгом порядке.
2. Остановить тестовый игровой сервер на период DDL и замены процедур;
   MySQL DDL не полностью транзакционно. Применить
   `db/migrations/019_bond_fund_core.sql` строго **один раз**.
3. Проверить наличие 19 в `schema_migrations`, полей казны, таблиц и
   актуальных дефиниций `treasury_post` / `gov_transfer_post`.
4. Убедиться, что B,F,E равны исходному балансу казны,0,0,
   а `bond_fund_enabled=0`; миграция **не создаёт начальные деньги**.
5. Запустить тестовую сборку MySQL-primary. Убедиться в сообщении
   `[GOV-01] Fund ready. Reserved=0, committed=0, enabled=0.`.
6. На staging выполнить отдельно подтверждённую тестовую капитализацию,
   списания через обе процедуры, проверку 80%-го лимита и replay.
7. Проверить серверный лог, idempotent event keys, поля версии и журналы.
8. При ошибке миграции остановить развёртывание, не выполнять
   непроверенный ручной rollback после необратимых DDL, сверить
   схемы с backup и восстановить на выделенной тестовой БД.

### Минимальные SQL-права

`bond_fund_capitalize` и `bond_fund_commit` — `SQL SECURITY INVOKER`.
Для нового функционала runtime-пользователю требуются
`EXECUTE` на процедуры и соответствующие ограниченные DML-права:

- `SELECT` и `UPDATE (bond_fund_reserved,bond_fund_committed,row_version)`
  на `treasury_accounts` (дополнительно к прежним правам).
- `SELECT,INSERT` на `bond_fund_ledger`.
- `INSERT` на `bond_fund_guarantees`.

Настройки (включая `bond_fund_enabled`, покрытие, ставки) должны
редактироваться только выделенной административной ролью в будущей
контролируемой процедуре с `bond_fund_config_version`. Прямые SQL
операции на production для изменения финансовых данных не разрешены.

**ПРИМЕЧАНИЕ О БЕЗОПАСНОСТИ:** `SQL SECURITY INVOKER` означает,
что при компрометации runtime-учётной записи её DML-привилегии могут
быть использованы напрямую, минуя процедуры. Перед публичным
запуском GOV-06 потребуется переработка модели привилегий на
контролируемые процедуры `SQL SECURITY DEFINER` с отдельным
минимально-привилегированным DEFINER и снятием прямых DML-прав
с игровой учётной записи; без этого механизм лишь защищает
официальные серверные операции, а не DB-компрометацию.

## Технические ограничения и требования следующих этапов

- Поскольку Pawn `cell` знаковый 32-битный, кэшируются лишь B,F,E
  в пределах 2 млрд; SQL умножает гарантии и процентные значения
  в 64-битной арифметике. Pawn считает доступный лимит через безопасное
  деление, без переполнения.
- `bond_fund_guarantees` ещё не имеет FK на `government_bond_issues`,
  потому что таблица выпусков появится позже. GOV-02 обязан связать
  фиксацию выпуска с `bond_fund_commit` в ОДНОЙ SQL-транзакции,
  а не использовать два независимых вызова с возможным рассогласованием.
- GOV-02/03 должен хранить условия покрытия каждого выпуска неизменяемыми;
  изменения настроек фонда не могут уменьшить права существующих владельцев.
- GOV-03 должен при страховке атомарно уменьшать B,F,E и оставшийся
  государственный долг, записывать связанные денежный и фондовый ledger,
  выполнять офлайн-платежи и исключать повторную выплату.
- GOV-01 фондовые процедуры не вызываются автоматически — интерфейс
  управления и независимые проверки полномочий появятся на следующих этапах.
- Все шаги подтверждаются автоматической сборкой и MariaDB UAT; финальная
  ручная пользовательская приёмка — **только всей системы целиком**.
